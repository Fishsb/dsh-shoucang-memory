# ADR-0005：知识整理核心抽离 + 双插件归属路由（泛用元记忆 vs 项目知识）

> 状态：accepted（2026-09-06 用户拍板启动执行）

## 背景

记忆插件职责收缩后（MEMORY.md 46 条中 ~33 条属开发场景，应迁往项目库），暴露一个架构缺口：

1. **蒸馏→固化链路整体内嵌在记忆插件**（`dsh-managing-memory/src/index.ts`）：watcher / 预筛 / extractDelta / spawn 蒸馏子代理 / 裁决提示词 / 入册，全写死记忆库路径与 `notes/` 白名单。它是「会话 → 蒸馏 → 裁决 → 分库写入」的**通用知识整理能力**，却被绑死在个人记忆这一个目标上。
2. **裁决缺第一层归属路由**：蒸馏子代理的四问只判「记忆内部三类」（env/tool/user…），**没有「真·泛用元记忆 vs 项目相关知识」的先决分流**——这正是职责收缩要的机制：开发坑默认落项目库，记忆库只收人脑级通用知识。
3. **开源/复用诉求**：本技能仓 `Fishsb/dsh-managing-memory` 与 pmg 仓 `Fishsb/dsh-project-map-governance` 均为开源；用户要求「插件可单独使用、后续记忆插件与项目插件都依赖这个整理知识文档、双装不重复」。现架构下项目插件无法复用记忆插件里内嵌的蒸馏引擎，双装必然重复实现。
4. **固化写入端已近可泛化但被白名单卡死**：`memory-append.mjs` 已支持绝对路径目标（`isAbsolute` 分支），但白名单只放记忆 `notes/7件 + 三索引`——非记忆文件一律拒绝。抽离的关键卡点就在这层写门。

## DSH 原生能力对照（架构拍板审查门，2026-09-05 补强）

> 立此门的教训：方案 B/C/D 用文件轮询+CLI 子进程+多套状态机重新发明了 DSH 原生会话生命周期观测，
> 孵化 9 轮补丁。新架构决策必须先证明「DSH 原生没有对应能力」才允许自建。

| 需求 | DSH 原生能力（源码/类型佐证） | 本决策是复用原生还是自建？为何 |
|---|---|---|
| 会话蒸馏触发（turn 结束 + idle 判定） | `session/event` 的 `turn/end`（reason.kind=completed）+ `agent.session.header.origin` 排除 subagent（ADR-0004 已实证） | 复用原生（ADR-0004 已落地，抽离只搬不重写） |
| 增量正文提取（内存零扫描） | `agent.session.snapshotEvents()` + event seq 水位 | 复用原生（ADR-0004 已落地） |
| 子代理裁决（LLM 归类） | `ctx.subagents.start('spawn')`（方案 D/E 已实证） | 复用原生 |
| **目标库注册 / 多插件共享单一引擎** | **无原生能力**：DSH 无「知识库注册表」概念；插件间共享需自建轻量机制（约定式文件注册或 ctx 服务） | **自建最薄层**：核心引擎唯一 + 目标库注册表（白名单参数化），避免重复蒸馏/重复裁决 |
| **领域路由（泛用 vs 项目）判定** | 无原生（这是 LLM 语义判断，非宿主能力） | 自建（裁决提示词升级：第一层 route 判定输出 JSON 加 `route` 字段） |
| **项目知识卡库写门**（docs/devref/ 卡 + INDEX + 门禁） | 无原生（pmg 现有 devref 只拉官方文档，非 agent 知识卡） | 自建（pmg 侧新增 devref 卡库能力） |

## 决策

1. **核心引擎并入技能仓**：把「watcher / 预筛 / extractDelta / spawn 蒸馏子代理 / 裁决提示词 / knowledge-append」从记忆插件抽出，放进 **Fishsb/dsh-managing-memory 技能仓的 `engine/` 子目录**（复用 pmg ADR-0002 的「engine/ 子目录 + 插件薄包装」成熟模式；技能仓本身就是开源单仓，核心随仓发布，无需新增包）。记忆插件与项目插件都薄包装指向同一 engine → **单一事实源，双装零重复**。
2. **裁决提示词加第一层归属路由**：蒸馏子代理先判「真·泛用元记忆？」，是 → 记忆库（现有四问 Q0/Q1/Q2/Q3 续）；否 → 「项目相关？」，是 → 项目库（how-to/reference/decision 卡），否 → 丢弃。输出 JSON 加 `route` 字段（memory|project|discard），宿主按 route 分流。
3. **写入端泛化**：`memory-append.mjs` → `knowledge-append.mjs`（目标白名单参数化：记忆 notes/ + 三索引 / 项目 docs/devref/ 卡 / pending/），保留安全阀语义（写前备份 / 容量门禁 / 小节锚拒写）。
4. **记忆插件瘦身**：只留目标库注册（记忆库白名单传参）+ 记忆侧四问裁剪（只收泛用）+ 记忆侧工具；蒸馏引擎本体移出。
5. **pmg 插件新增项目知识卡库**：`docs/devref/` 下 how-to/reference/decision 卡 + INDEX + 写门（`devref_write_gate`），承接开发坑/契约/SOP/架构决策；项目 AGENTS 写双查纪律。
6. **插件契约**：核心是唯一注册者；记忆插件 = 注册记忆库为目标；项目插件 = 注册项目库为目标。单装只写对应库，双装蒸馏一次、路由分流两库。
7. **开源隐私红线不变**：engine 只含规则/脚本/模板，不含用户画像/本机路径/会话数据（README 已声明）。

## 后果

- 正面：记忆插件回归纯「人脑」定位（注入面 44→~10 条）；开发知识有专职承载（pmg 卡库 + 治理门禁：核验日期/触点回查——记忆库从没做到的）；蒸馏引擎单处实现、记忆/项目双插件即插即用；开源后任何 DSH 用户可独立装任一插件，双装无重复唤醒/重复裁决。
- 副作用：多一层 engine/ 目录维护（同步 src/lib 的既有边界仍在）；归属路由依赖 LLM 裁决质量（宁缺毋滥四问仍是兜底）；pmg 侧需新增卡库能力（独立立项）。
- 风险缓解：抽离只搬 ADR-0004 已验证的事件链路（不重写）；knowledge-append 保留备份/容量/锚门禁；route 判定失败默认 discard 或回记忆 pending（不丢内容）。

## 替代方案

- **新独立包托管核心**：更解耦但多一个发布维护面——弃（技能仓 engine 单仓可移植、少维护）。
- **抽进 pmg 托管核心**：记忆插件依赖 pmg，纯记忆用户被「项目治理」绑架——弃。
- **维持内嵌，项目插件自己实现蒸馏**：双装重复唤醒/重复裁决、规则双写漂移——弃。
- **归属路由放记忆侧规则文件而非裁决提示词**：规则文件只在记忆上下文生效，项目插件读不到——弃（路由必须在核心裁决层）。
