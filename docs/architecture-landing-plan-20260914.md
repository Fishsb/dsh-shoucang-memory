## 0. 为什么必须分阶段，以及为什么阶段 0 不能跳

本轮要动的是**运行时行为**（产线续传格式、注入文本生成路径）。一次性全量改完再验证，
一旦出问题无法定位是哪个改动引入的。分阶段的真实价值不是"排期"，而是**每个阶段都可独立回退**。

**阶段 0（门禁底座）绝对不能跳。** 理由：当前所有架构门禁都是绿的（见 §1），
但这是"阈值宽松导致的恒绿"——最大模块 880 行，而模块行数门禁是 2000 行，
**这条门禁今天谁也碰不到**。先立门禁再动刀，才能让"改动把模块堆大了"立刻变红。
先拆后立门禁 = 拆的过程中堆回去，无人察觉。

## 3. 阶段 0 · 防堆叠门禁底座

### 0.1 大模块禁止增长名单（核心机制）

对 **≥600 行**的模块（`treeops 880` / `panel-shared 802` / `scheduler 746` / `mcl 618`）

## 4. 阶段 1 · 隐式通道显式化

**目标**：把"通道建了、通知没建"补完，消除隐式契约的漂移风险。

### 1.1 上游落盘主动失效注入缓存

现状：`invalidate`（`panel-shared.ts:328`）**只由面板写触发**；蒸馏/深睡落盘不触发，
靠 TTL（30s / 120s / 60s）自然过期 ⇒ 刚蒸馏出的记忆最坏 120s 内注入看不到。

做法：**复用现成的 `sizeStampOf`**（`panel-shared.ts:388`，文件尺寸签名，零依赖零 spawn），
把稳定面缓存键从"3 个索引文件"扩展到"索引文件 + 4 个产线介质"。
**零跨半区耦合**——不需要让 scheduler 半区回调 panel 半区，避免重蹈三条桥的覆辙。

### 1.2 消副本 —— **已撤销（前提不成立）**（2026-09-14 复核）

### 1.5 验收发现：本阶段的**收益主张不成立**，签名接错了缓存层（2026-09-14 · 已修）

> 本节是对 §1.4 那句「产线一落盘，注入缓存**立即**失效，不再等 120s TTL」的**实测订正**。
> 该主张在**正向测试下永远为真**，所以它一路绿到了验收才被抓住。

**症状（假绿）**：「缓存键变了、**输出没变**」。两条实测：

1. 改 `activity.jsonl` 尺寸 ⇒ 稳定面**逐字节不变**（248 字符）⇒ 三条介质对稳定面**无内容贡献**；
2. 决定性 —— 改 `activity.jsonl` 使内容确有影响后：**同 query 紧接重调输出不变**、**换 query 立刻变**
   （后者是对照组，排除"判据失效"）。

**根因**：把关**整段文本**的是 `buildHotMemoryText` 顶部那个 **30s 的 `cacheKey`**（`memRoot|q`，无签名）；
而 §1.1 把签名接在了 **120s 的 `stableKey`** 上，而稳定面只装画像段 ⇒ **重算买不到任何内容更新**。
§1.1 的"把稳定面缓存键从 3 个索引文件扩展到 4 个产线介质"这个**落点本身选错了**。

**修法**：① 签名**移到 `cacheKey`**；② 介质集**去掉 `warm-recall.json`**——它一次只装**一个 query** 的行，
签它会「为 query B 的写入失效 query A 的缓存」而 A 输出不变 ⇒ 正是判据禁止的"平白失效"；
③ 稳定面键恢复为只用 `AGENT.md`/`USER.md` 尺寸。
**内容零变化**：修复前后同输入 `build()` **sha256 四组全等**（只改"何时重算"）。
**补测试**：新增 `test-inject-cache.mjs`（14 条断言，已登记 `CHECKS`，全量 **77 pass**）。
详见 `docs/adjustment-plan-20260914-stage1-cache.md` + `docs/acceptance-plan-20260914-stage1-cache.md`。

> **本阶段最值得记的方法论**（已并入验收方案 §0.2 第 4 条）：
> 凡「××立即生效」的主张，判据必须落在**输出**上；只验"缓存键变了"会**恒定假绿**。
> §1.3 原本的验收判据「模拟产线落盘后，注入缓存键必须变化」正属此类——**它验的恰好是那个没用的信号**。

## 5. 阶段 2 · 产线流程实例

**目标**：把续传状态从"一个数字"升级为"可回答卡在哪一步"的流程实例。

### 2.1 现状与缺口

| 产线 | 续传状态 | 存放 | 重启后 |
|---|---|---|---|
| 蒸馏 | `lastSeq` 一个数字 + 双证 | `audit/distill-watermark.jsonl` | 可读回，从最后成功 `endSeq` 续 |
| 深睡 | `lastDeepSleepAt` 时间戳 | 内存（`deepsleep-machine.ts:16-21`） | 从审计日志回放重建 |

内存态 `distilling` / `dispatchFailStreak` / `skipHoldStreak`（`distill-state.ts:16-22`）**重启清零**。
连带缺口：`distill-agent.ts:241` 只在段末写审计，spawn 前无 start 审计；
`getDeepSleepStatus` **不含蒸馏进度**，面板查不到"正在蒸哪段"。

### 2.2 做法

水位从标量升级为：`{ runId, phase, startedAt, updatedAt, attempt }`，**落同一个 jsonl**。

- **向后兼容是硬要求**：磁盘上已有旧格式水位文件，读时必须双格式兜底
  （旧格式 ⇒ 视为 `{ phase: 'unknown', attempt: 0 }`）。
- **不引入工作流引擎**：三步以内、无长时等待，手写状态表更轻。
- 深睡侧同构处理，并让 `getDeepSleepStatus` 暴露当前 phase。

### 2.3 验收判据

- 新单测 `test-run-instance.mjs`：旧格式水位可读 / 新格式可读 / 崩溃重启后续到正确 phase
- `test-distill-source-filter`、`test-deepsleep-verdict`、`test-watermark-guard` 保持绿

## 8. 治本机制：如何保证"代码不堆叠"

阶段 0 的门禁是手段，真正防止堆叠的是下面五条。建议写进 `AGENTS.md`：

**M1 · 大模块冻结（**带容差**，2026-09-14 用户反馈后修正）**：≥600 行的模块登记基线，
只允许在**容差带**（当前 15 行）内波动，超出即红；必要的大幅增长走 `--rebase` 显式回写
（写进 git diff，进得了 review）。
> 为什么必须有容差：写死"只许降不许升"过于刚性——加几行注释、加一个分支都会被拦，
> 于是开发者要么放弃这次合理改动，要么**为了过门禁把内聚的代码硬切**。
> 后者比堆积更有害（见 M6）。
> **容差是波动缓冲，不是可支配额度**——故容差内也会打印提示，防止被当成"还能加 15 行"。

> **基线重设点在「阶段收尾」**（2026-09-14 执行阶段 1 时确立）：
> `--rebase` 不是"给门禁让步"，而是流程的一部分——**阶段内不许涨，阶段边界允许重设一次**。
> 前提：重设时必须在交付记录里写明**增量构成**（多少是功能代码、多少是注释），
> 否则"每次 rebase 一点点"会退化成慢性膨胀，门禁名存实亡。

**M2 · 新功能落新模块**：模块数应随功能增长；单模块行数趋势向下。
**M3 · 棘轮只许收紧**：所有门禁基线只降不升（既有纪律，扩展到本轮新增的 3 项）。
**M4 · 禁止恒绿门禁**：新设门禁必须满足"当前至少有一个对象接近它"，
否则就是假绿（本轮教训：模块行数 2000 对最大 879 而言恒绿）。
**M5 · 单一实现 + 机检**：跨域依赖一律登记并双向机检（本轮扩展到"文件通道"这一类隐性依赖）。

**M6 · 按接缝拆，不按行数切**（2026-09-14 用户反馈后补）：**行数是信号，不是目标。**
硬切内聚的代码比堆积更有害——切错接缝 = 把一个内聚体拆成两个互相依赖的碎片，
行数好看了、可维护性反而变差。拆之前先回答"这一块的**领域边界**在哪"；
回答不出就先别拆，**宁可让它大着，也不要制造碎片**。
判据：拆完若两模块间出现双向依赖或大量跨模块调用，就是切错了。

> M4 是本方案最重要的方法论产出：它与"永久红灯人人无视"是同型问题、方向相反。
> **每加一条门禁都要自问：当前有人碰得到它吗？**
> M6 是同等重要的第二条：**门禁守的是信号，不是形状。** 为达标而切坏的模块，比超标的大模块更难收拾。
