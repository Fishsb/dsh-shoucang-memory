## 2. 核心诊断：「内容类型」在当前架构中不是一个层

你的顺序假设「先调核心内容类型」——但实测显示，**内容类型没有单一权威定义处**，它裂成三份、彼此不引用：

| 分散处 | 内容 | 位置 |
|---|---|---|
| ① 载体契约 | 15 个标签 × `layer(P/R/E)` + `form` + `inject(always/gated/none)` | 【注册表】`criteria.json#carriers` |
| ② Record kind 枚举 | `blank/structure/procedure/persona/fact/prose` + 环 7 类 | 【读码】`record-store.ts:147-155` + `MemRecord.kind` |
| ③ md 行形态 | 索引行 `[tag] … → notes/x.md §y` / 画像行 `- [tag] … ← 源:` | 【读码】`targets.ts:281-306` |

**三者关系未被任何一处声明**：

- ① 管"**哪些标签能进哪个注入面**"，② 管"**数据库里的类别**"，③ 管"**人读文件的语法**"
- `kindOfLine` 从 ① 的 `layer` 派生 ②（`:150-153`），但**反向不可达**：② 中 7 类环 kind 在 ① 里**没有对应标签**（`carriers` 里没有 `decision`/`episode`/`valence` 等）
- ③ 的标签集与 ① 部分重叠但**无一致性机检**（`check-carriers` 只查 ① 内部三字段合法）

⇒ **"调内容类型"这个动作在现有结构里没有落点**。它不是"改一个文件"，而是要**新建一个层**。这正是本问题最根本的答案：**不是顺序问题，是缺一个层的问题**。

## 3. 顺序的依赖判定

### 3.1 判定方法：看"决定方向"，不看"数据流方向"

数据流方向是 生产 → 库 → 消费，容易得出"从头改"。但**决定方向相反**：

| 关系 | 谁决定谁 | 证据 |
|---|---|---|
| 生产 → 库 | 生产**决定**产什么形态 | `distill-write` 的 `writeDispatch` 决定写 md 还是环 |
| 维护 → 库 | 维护**决定**如何重写已有内容 | `deepsleep-apply` 做指针/索引/树操作 |
| **库 → 消费** | **消费决定库的形态**（实际发生） | 恒定面只认 `^[tag]` 且 `inject=always`（`targets.ts:303`）；动态面只认 `→ notes/` 指针（`scanIndexRows:334`）；画像行只认 `- … ← 源:`（`isProfileRow:296`） |

**"消费决定库的形态"是本项目已发生的事实**：那 105 条环记录之所以不可达（`docs/library-supply-chain-rework-2026-09-14.md` §1.2），正是因为**生产者按自己的方便写了库，而消费侧的读法早就定死了**。

⇒ **结论：内容类型的边界必须由消费判据倒推，不能凭空定义。** 否则会重演"产出了、没人能读"（105 条 = 3.9% 的库内容当下处于此状态）。

### 3.2 修正后的顺序（推荐）

```
① 冻结「内容类型契约」（新建层）
      ↑ 输入来自 ↓（反向）
   消费需求盘点：每类信息在什么情境、被什么判据、命中后做什么
   —— 这一步只读代码与数据，不改任何行为
        ↓
② 按契约调整【维护链条】—— 先于生产
      理由：维护链是唯一能重写历史的环节；契约变更须先对存量 1,177 条做对齐
        ↓
③ 按契约调整【生产链条】
      理由：只影响增量；且它有"少写数据"的自由度（见 §3.3）
        ↓
④ 实现【消费链条】的对应通路
      理由：让新类型可达；此步是"让前面三步有意义"的收口
```

### 3.3 为什么维护链条先于生产链条

**关键不变量：契约变更必须先对历史数据达成一致，否则新老两种类型并存会污染消费面的统计与判据。**

但要区分两类变更：

| 契约变更类型 | 维护链条 | 生产链条 | 谁先 |
|---|---|---|---|
| **新增类型**（例如让 episode 有载体） | **不需要**重写历史（历史无此类型） | 需要按新契约产出 | **生产先**，维护不动 |
| **改变已有类型的语义**（例如 `[原则]` 分层规则改变、标签重命名） | **需要**批量重写存量 | 只需改增量 | **维护先** |

⇒ 严格说法：**顺序取决于契约变更的类型**。但工程上有一条统一解：

> **先调维护链条，不是因为它总要先行，而是因为它把"契约对存量的适用性"一次性钉死**。维护链先跑一遍存量对齐（即使结果是"无需改动"，也要**显式确认**），之后生产链再改增量，就不会出现新老并存。
> **若维护链条后调**，则生产链已按新契约产出新数据，而存量仍是旧契约 ⇒ 消费面同时面对两种形态，判据与统计全部失真，且**失真期间产生的数据会二次污染**。

### 3.4 与"标准制定"的类比【判读】

这是接口优先（interface-first）原则的实例：**先冻结协议，再改两端**。但本项目多一层特殊性——**协议本身需要从既有消费者的实际出发倒推**，而不是从生产者能产什么出发。理由：生产者只对"能产出什么"负责，消费者对"什么有用"负责；而 §3.1 已证明**决定方向是消费者 → 库**。

## 4. 执行手册（每步的约束与验收）

| 步 | 动作 | 硬约束 | 验收判据 |
|---|---|---|---|
| **①契约** | 新建内容类型权威定义（建议落在 `criteria.json` 新节，与 `carriers` 并列而非混入） | 必须**声明 ①②③ 三处的关系**（谁派生谁、谁是事实源）；机检守住 | 机检能回答："kind=X 的记录由哪个标签/形态承载、能否被哪条通路取到" |
| **②维护** | 按契约对存量 1,177 条做对齐（迁移/重投影/提纯） | 干跑对账（仓内既有原则：**干跑记预期动作数，实跑须零差异**）；原子写；备份 | 存量对齐后**逐类可达性**可枚举；未对齐项有清单与理由 |
| **③生产** | 改 `distill*` 的写入分发使增量符合新契约 | **必须先解决 F1（深睡归属）**，否则要动已顶格的 I1 装配函数 | 新产出 100% 合契约；旧格式产出为 0（机检） |
| **④消费** | 实现新类型的通路（含 `situation` 槽扩容、内容面合并） | 见上份方案 §5 施工卡（A1–A3 / B1–B2 / C1–C2 / D1 / E1–E2） | 每类信息的"命中率"可实测（当前：环记录命中上限 3 条 / 105 条） |

**双写期护栏**：②与③之间必然存在"存量已对齐、增量未改"的窗口 ⇒ 该窗口内**消费面必须保持旧判据**（否则读到半新半旧），直到③完成再切④。
