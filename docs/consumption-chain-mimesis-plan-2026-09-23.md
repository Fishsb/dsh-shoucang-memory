## 3. 中层方案（本轮唯一可施工项）

### 3.1 第一施工项 = **结论回流通道**（不是修 `acted`）

**为什么它是第一项**：
```
配对检验：窗 60s → 0/10 · 窗 3600s → 0/10 · 窗 86400s → 10/10（同日巧合）
两边时刻跨日错开：步内出口活跃于 09-21/22；模型语义判定主力在 09-16（9/14 次）、末次 09-23
再加硬证：src/mcl.ts 全文零 readFileSync ⇒ 物理上不可能读离线产物
```
⇒ 离线已判出的「该换向」**对步内行为零影响**。「机制在场、判据哑火」能长期共存的原因即：**观测面在响、行为面不响，二者无人对账**。

### 3.2 为什么不能只修 `acted`（D5 数据反证）

| 只修成因1的两种调法 | 后果 |
|---|---|
| **窗口放宽**（近采集器口径 85%–99% 非空） | `zeroGain` 要攒到 2 需连续两步无动作 ⇒ **近乎不可达** ⇒ 与今天同形的**恒假** |
| **窗口收窄**到能触发 | 退回 **D5 之前形态**（`zeroGain` 39 取值 / `switchSource` 114 行），而那时的换向来自**词面回代理由** ⇒ **恒真/随机翻转**型第二类假绿 |

⇒ **成因1 是成因3 的输入整形，不是独立修复项。** 两者必须**同批**。

### 3.3 用户新原则的适用点（判断者替换，非代理替换）

| 分派 | 内容 |
|---|---|
| **须升级模型判断** | ① 步级「这一步有没有实质推进」（缺口①核心）② 外层 L2 理解 + 效能估计 ③ 内层情境配对（`cue` 是否真是"同一情境"——字符串全等是机械匹配，语义近邻它答不了） |
| **必须保留确定性**（禁调模型） | 水位与段边界 `segKey` · 格式门 · 隐私红线 · 账目守恒与真实裁切 · 幂等与原子性 · 路径白名单与预算 · cue 归一与维校验 |

**张力划法（与 `notes/flows.md §判据分工` 不自相矛盾）**：
1. **按判断对象性质分派**——可机检的**事实**（发生没发生/几条/账平不平）⇒ 确定性；不可机检的**语义**（有没进展/像不像同一情境）⇒ 模型。
2. **模型判必须带"未判"态，且未判不得兜底**（复用既有 `parseYieldJudgements`「任一不合法⇒整批 null」+ `switchFromJudgements`「null 打断链」，**照抄不新造**）。
3. **模型输出不得进入确定性门**；只能当候选/信号，且须落审计可分辨来源。
4. **频率解法**：模型判**不得落在每步路径上**——步内只做确定性**筛候选**，模型判按**轮**触发，结论回流步内。（每步新增 IO=0 / 嵌入=0 / 召回=0，与 M3a「高频那一半必须廉价」自洽。）

### 3.4 ⚠ 关键警告：**"上模型"不是充分解**（本仓已在线路径自己就在失效）

```
59 行模型判定：helpedTrue = 0（历史上一次都没判过 true）
三态读数「未判」只活在 yieldNote 中文串（"判 10（帮上 0 · 未判 10 · 注入后有动作 10/10）"）
yieldUnjudged / yieldError 字段存在 = 0 / 0  ⇒「判不准」与「判不了」当前【不可分辨】
```
**同文件同天的不对称修复（本轮最硬的对照）**：`deepsleep-run.ts:579` 的 `releaseSemanticError` 已按 ACT-352 修复（注释明写「`undefined`=判定完成；有值=判定未完成 ⇒ 消费侧必须读此字段，不得据 `approved===0` 推断」），而**同一行 `:573`** 的 yield 侧**独缺**对应字段 —— **修了一个，漏了另一个**。
⚠ 且 obs 实测：**ACT-352 的修法自己也在正常分支失效**（`releaseSemanticError` 正常时为 `undefined`，被 `event-envelope` **静默丢键**：54 行带 `releaseSemantic*` 的行，含该键 **0** 条）。
⇒ **字段契约必须用「键缺席 = 判定完成」形态**（`'error' in o` 判定），**不能用 `undefined`**（否则新字段自己就是下一个静默失效）。

⚠ **诚实的运行态缺口（2026-09-23 复验后订正 · ACT-363 / ADR-366）**：
本节原写「链条已通（S2 写侧 + S3 读侧 + S4 字段都在位）……端到端闭环要等下一轮深睡」——
**该结论已被复验推翻**：写侧确实落了 `yield.verdict` 行，但**读侧永远认不到它**。三处静默失效叠加（均 fail-closed ⇒ **不报警、只静默不工作**）：

| # | 缺陷 | 实测证据 |
|---|---|---|
| ① | **键口径两侧相反**：读侧 `slice(-8)` vs 写侧 `slice(0, 8)`；真机 `agent.id` 是长形 `session-<uuid>` | 活体面板 `sysBlockLastSid="session-7de99a"` + 轨迹 `renSame`；端到端：喂长形 ⇒ `undefined`，喂短形 ⇒ 才读到 |
| ② | **取样器恒指向死会话**：原按 `idleSteps` 降序（该键被采集器封顶 3 ⇒ 实测 **85.2% 并列最大** ⇒ 排序键饱和） | 稳定排序取到**最老 10 行**（全为 2026-09-15，sid `6be5ac2e` 末次活动 09-16） |
| ③ | **尾读窗口小于字节窗**：缺省 200 行 vs `readTailLines` 256KB（≈730 行）⇒ 读了丢弃 ~73% | 同一行 `perVolume=200` **MISS** / `300` **HIT**；台账 4.8 行/分 ⇒ 约 42 分钟后必超 200 |

⇒ 三处已各收敛为**单一实现**并修复（`shortSidOf` / `sampleYieldRounds` / 缺省窗口 1000），三件测试各带**反向自证**（变异实测均能抓住）。
⚠ **仍存的诚实边界**：修后证据为**函数级 + 真库读数**（长形键可读到那行、取样指向活会话），
**尚未**观察到「真机深睡产出 verdict ⇒ 活会话据此换向」的**完整闭环**——需下一轮深睡，
且上游 Ollama 嵌入通道自 18:09 起不可达 ⇒ 判定多半仍 `unjudged`（**这与"通道修好了"不矛盾**：通道是通路，判定质量是另一回事）。
这正是 `check-yield-reflow` 仍判 xfail 的原因，也是它**转绿即退 1** 的设计意图。

**关键顺序约束**（arch 席）：**S2 与 S3 必须同批**——单做 S3 必产第二个假绿。
**提交纪律**：**删除面与新增面分两个提交**（先删 `acted`/`nextZeroGain` 净减可独立回退，再落 verdict 流净增）。
