> 制定日期：2026-09-14 · 依据：`deliverables/acceptance-review-2026-09-14.md`（验收结论：不通过）
> 上游：`docs/architecture-landing-plan-20260914.md` §4（阶段 1 原始设计）

## 0. 一句话

验收把 B1 从「判据 2 不通过」钉成了**机制结论**：三条介质签名接在 **120s 稳定面键**上，
而真正把关整段文本的是 **30s query 缓存键** ⇒ 方案 §1.1 声称的「产线一落盘立即失效」**收益为零**。
本方案把签名**搬到真正把关的那一层**，并同步补上验收缺的那件单测（B2）。

## 1. 问题（实测，非推断）

| # | 事实 | 证据 |
|---|---|---|
| 1 | 改 `activity.jsonl` 尺寸后**稳定面逐字节不变** | 独立探针，248 字符 |
| 2 | 改 `activity.jsonl` 使**内容确有影响**后：**同 query 重调输出不变**、**换 query 立刻变** | 同上（后者是对照组，排除"判据失效"） |
| 3 | 阶段 1 **全仓零单测** | `upstreamStampOf｜sizeStampOf｜createHotMemory｜stableKey｜invalidate(` 在 `scripts/`+`skill/` 零命中 |

**机制**（读码佐证）：`buildHotMemoryText` 顶部
`if (cache.key === cacheKey && now - cache.at < 30000) return cache.text` —— `cacheKey = memRoot|q`，
**不含任何介质签名**；而 `stableKey`（含签名）只装**画像段**，三条介质影响的 `memLines`/一次性块**不在其中**。
⇒ 「缓存失效了，但输出没变」——**正向测试天然看不见**，这正是它能瞒过历轮验收的原因。

## 2. 决策

### 2.1 介质逐个判（按**变更频率 × 是否绑定查询**两类事实决定）

实测（2026-09-14 19:28）：`activity.jsonl` 与 `delta.md` 的 mtime 同为 **Sep 13 18:17（隔天级）**；
`warm-recall.json` mtime **当天 18:57**，且内容是 `{at,key:"t5xtif:13",rows:[…]}` ⇒
**按查询键绑定、单查询级写入**。

| 介质 | 是否影响输出 | 变更频率 | 查询域绑定 | 决定 |
|---|---|---|---|---|
| `audit/activity.jsonl` | 是（冷热排序 → 变动面） | 隔天级 | 否 | ✅ **签进 `cacheKey`** |
| `delta.md`（深睡产物） | 是（一次性块） | 隔天级 | 否 | ✅ **签进 `cacheKey`** |
| `audit/warm-recall.json` | 是（召回行 → 变动面） | 查询级 | **是**（只存一个 query 的行） | ❌ **不签** |

**为什么单把 `warm-recall.json` 排除**：它一次只装**一个 query** 的行。
若签它的尺寸，则「query B 的预热写入」会失效「query A 的缓存」，而 A 的输出**根本不会变**
（key 不匹配即回落词法通道）——这正是判据 2 明令禁止的「**平白增加失效次数**」。
其代价是 A 最多晚 30s 看到自己的预热行，且**缺失时语义正确**（回落词法召回）。
⇒ 宁可不签，也不签一条**会为别人抖动**的键。

### 2.2 被否决的选项（留痕，避免日后重议）

| 选项 | 否决理由 |
|---|---|
| **A. 三条都签进 `cacheKey`** | 简单，但 `warm-recall.json` 会为**别的 query**的写入反复失效本 query 缓存 ⇒ 与判据 2 精神冲突（§2.1 已论证） |
| **B. 同时留在 `stableKey`** | 稳定面内容与这三条介质**无因果关系**（实测事实 1）⇒ 留一份只增重算，不增收益 |
| **C. 不签、只把 30s 调小** | 治不了"落盘即时"，且全局面变慢；且 `delta.md`/`activity` 本就是**罕见变更**，签名成本近零 |
| **D. 引入文件监听（fs.watch）** | 跨域通道 + 生命周期/跨平台风险，与「单一实现 + 机检」纪律冲突；签名已够 |

### 2.3 目标态

```
cacheKey  = memRoot | q | upstreamStampOf(memRoot)      ← 新增：真正把关的那一层
stableKey = memRoot | personaMode | profileCap | 尺寸签名(AGENT.md, USER.md)   ← 去掉 upstreamStampOf
upstreamStampOf = 尺寸(activity.jsonl) | 尺寸(delta.md)   ← 去掉 warm-recall.json
```

## 4. 本轮不做（明确排除）

| 项 | 理由 |
|---|---|
| **B3 宿主热重载** | 环境侧动作，需用户执行（入口 `dev_reload_package`）。本方案只保证"仓内 + 已部署"，**不宣称运行态闭环** |
| **N2 稳定面键只含尺寸**（同尺寸改内容 120s 内不可见） | 既有低危限制，非本次引入；面板写入走 `invalidate()` 已覆盖，产线追加必改尺寸 ⇒ 暴露面窄。**登记为已知限制**，不顺手改（避免把"修一个错层"扩成"改注入内核"） |
| `warm-recall.json` 的 30s 窗口 | §2.1 已论证为**可接受**（缺失回落正确） |
| 合并两条缓存层 / 重构缓存设计 | 超出本修复范围；留待有实测收益需求时单独立项 |

## 5. 风险与回退

| 风险 | 评估 | 处置 |
|---|---|---|
| 改了缓存失效时机，注入**内容**被意外改变 | 低——只动键的构成，不动求值 | 验收判据 S7：修复前后同输入 `build()` **sha256 必须全等** |
| `activity.jsonl` 若被高频写入 ⇒ 30s 缓存频繁打穿 | 低——实测**隔天级** | 验收记录实测 mtime；若将来变高频，签名仍在**正确层**，只是收益/成本重新评估 |
| 新单测变成恒绿 | 中——这是本仓老坑 | 验收判据 R5：**必须反向证伪**（把签名从 `cacheKey` 拿掉 ⇒ 单测必须红） |
| 模块增长门禁 | 中——`panel-shared` 843 / 容差上限 846 | 目标**不加行**；若超容差走 `--rebase` 并按 M1 **写明增量构成** |

**回退**：单文件改动；`git revert` 本提交即可回到当前态（当前态已通过阶段 3 的逐字节实证，是安全基线）。

## 6. 纪律

沿用验收方案 §0.2 三条（结论与证据同源 / 否定前先列全变体 / **反向证伪不可省**），并追加一条本仓教训：
**凡"某改动买到了 X"的主张，必须有一条能区分"缓存没失效"与"输出没变"的判据**——
本轮 B1 之所以瞒过历轮，就是因为原判据只看了前者。
