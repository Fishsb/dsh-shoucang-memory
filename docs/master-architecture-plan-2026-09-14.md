## 0. 一页结论

**总目标**：**信息类型 → 消费时机的可达性完备**。每一类信息都必须能回答三个问题，且答案在**唯一一处**可查：

1. **谁生产它**（生产链条 / 维护链条 / 用户手工）
2. **它存在哪**（Record kind · md 投影 · 环记录）
3. **什么时候被谁消费**（三层中的哪一层、什么判据、什么预算）

**当前最根本的缺口**：这三个问题**在现有架构里没有统一落点**——

| 三问 | 现在散在哪 | 后果 |
|---|---|---|
| 谁生产 | 散在 `distill*` / `deepsleep*` 的写入调用点 | 数不出「某类型由谁供给」 |
| 存在哪 | 裂成三份且互不引用（载体契约 / Record kind / md 行形态） | "调整内容类型"**没有落点** |
| 何时消费 | 五条通路**全部挤在"任务开始"** | 中层（执行中）无供给；105 条环记录不可达 |

**一句话方案**：**新增一层「内容类型契约」，把四链条从"按代码位置分"重划为"按职责分"，消费侧按人类三层（任务/行动/认知）分时机供给，并让每一条供给都带自己的判据与预算。**

### 3.2 为什么要新增"协议层"（而不是在既有三处里挑一处）

**现状**：内容类型裂成三份且互不引用【读码】——

| 分散处 | 内容 | 位置 | 管什么 |
|---|---|---|---|
| ① 载体契约 | 15 标签 × `layer(P/R/E)` × `form` × `inject` | 【注册表】`criteria.json#carriers` | 哪些标签能进哪个注入面 |
| ② Record kind | `fact/persona/procedure/prose` + 环 7 类 | `record-store.ts:147-155` | 数据库里的类别 |
| ③ md 行形态 | `[tag] … → notes/x.md §y` / `- … ← 源:` | `targets.ts:281-306` | 人读文件的语法 |

`kindOfLine` 从 ① 派生 ②（`:150-153`），但**② 中 7 类环 kind 在 ① 里没有任何对应标签** ⇒ 环记录既不在恒定面、也不在相关性面（§2.4-G1）。

**协议层的形态（三选一，建议 A）**：

| 方案 | 落点 | 优点 | 代价 |
|---|---|---|---|
| **A（建议）** | `criteria.json` 新增 `contentTypes` 节 + `src/content-types.ts` 纯函数读它 | 与 B4 一致（判据唯一源）；纯函数零 IO 可单测；**不新增依赖** | 注册表变大（需 `check-criteria` 守形态） |
| B | 新建 `content-types.json` + 模块 | 关注点分离清晰 | 引入**第二个事实源**，与 B4 精神冲突 ⚠️ |
| C | 塞进 `carriers` 节扩展 | 改动最小 | 语义混装（载体≠类型），`check-carriers` 三字段校验会失守 |

**方案 A 的契约形状（示意，非最终 schema）**：

```jsonc
"contentTypes": {
  "principle": {                        // 内容类型 id
    "recordKind": ["persona"],          // 落到哪个 Record kind（② 的入口）
    "carrier": ["原则"],                 // 哪个 md 标签承载（① 的入口）
    "form": "profile",                  // 行形态（③）
    "producers": ["deepsleep", "distill"],
    "projection": "md",                 // md | none（决定可达性）
    "consumer": { "layer": "outer", "timing": "session-start", "criterion": "always" },
    "budget": "stable",
    "reachable": true
  },
  "decision": {
    "recordKind": ["decision"],
    "carrier": [], "form": "ring", "projection": "none",
    "producers": ["distill", "deepsleep"],
    "consumer": { "layer": "inner", "timing": "per-step", "criterion": "situation-key" },
    "budget": "situation",
    "reachable": true
  }
}
```

⇒ **从此"某类信息能否被消费"是一个可机检的字段（`reachable`）**，而不是靠人读代码推断。**这是本方案最核心的一处新增。**

### 3.3 四链条重划（按职责，不按代码位置）

| 链条 | 输入 → 输出 | 职责边界 | 与现状的差 |
|---|---|---|---|
| **生产链条** | 会话 → 库 | **只增不改历史**；按协议产基础数据 | 基本不变 |
| **维护链条** | 库 → 库 | **唯一能重写历史**：整合、提纯、纠错、遗忘、跨主题 | **须从 distill 内迁出（F1）** |
| **消费链条** | 库 → 上下文 | 按三层分时机供给 | 从"五通路平铺"改为"三层结构"（§4） |
| **协议层** | —— | 定义 type ↔ 生产/载体/消费的映射 | **新增** |
| 库核心 | —— | 事实源 + 三面（内容/经历/元）+ 时态 | 面划分显式化 |

### 3.4 库核心的三面模型

| 面 | 成员 | 投影 | 供给通道 | 预算 |
|---|---|---|---|---|
| **内容面** | `fact` · `procedure` · `persona` · notes 正文 | **md**（三索引 + notes） | 分层准入 → 相关性/新鲜度 | 一条（合并恒常+动态） |

【判读】这个划分**不是发明**——`supply-assembly` 的 `SupplyBudget` 槽位（`stable/dynamic/oneshot/situation`）已经隐含它。方案要做的是**把它变成唯一口径**。

## 4. 消费链条：三层供给结构

### 4.1 三层 × 内容类型映射

| 层 | 行为（人类对应） | 供给什么 | 时机 | 判据 | 现状 |
|---|---|---|---|---|---|
| **外层 · 任务级** | 预见 → 表现 → 反思 | 原则 · 偏好 · 边界 · **效能** | 会话开始 + 收尾 | 分层准入（always） | ✅ 做实（P 层 ~1756 字符），**缺效能** |
| **中层 · 行动级** | 行动 → 监控偏离 → 控制 | 路径 · **流程判据** · 偏离信号 · 到期承诺 | 任务开始 + **执行中** | 任务型 + 偏离检测 | ⚠️ **最空**（无专用通路） |
| **内层 · 认知级** | 情境感知 → 检索 → 判断 | 指针 · 情境记忆 · 事实 · 关联 | **每步** | 情境键 + 相关性 + 熟悉度 | ✅ 拥挤（通路 2/4/5） |

### 4.2 核心机制：判据常驻 + 材料按层按需

现状三者混装【读码】：**判据**在提示词（模型自愿、消费链条影响不到）· **材料**按"像不像"选（不分层）· **方向**混在常驻面抢预算。

```
常驻判据层（每步都在，三层合计 <200 字符）
  外层：念一遍任务目标与红线
  中层：连续 2 次无实质进展 ⇒ 停走回溯；线索变弱 ⇒ 换向；承诺到期 ⇒ 主动提
  内层：先情境键、后内容相似；证据冗余即停
        ↓ 触发才注入
材料层（按层、按情境、按需）—— 见 §4.1「供给什么」列
```

**项目已自发做了第一步**：`mcl.ts:165-169` 的 `THIN_CONTRACT` 就是一条极小判据——但**只在慢通道、只在任务首步**。本方案把它**推广到三层、全时机**。

【活体证据】本会话真实观测：慢通道注入 `判据域分治` / `深睡吸收过程数据` / `记忆质量审查` 三条，**相关性良好**；但三条全属内层与方向，**无一条提供"执行中的过程判据"** ⇒ 恰好印证中层缺位。

### 4.3 预算模型（单一实现 + 独立槽）

| 槽 | 归属层 | 缺省 | 现状 | 目标 |
|---|---|---|---|---|
| `stable` | 外层 | 吃余额 | 手写三层（G5） | 并入 `SupplyBudget` |
