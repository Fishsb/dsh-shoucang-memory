# S2 · 生产链条方案（会话 → 库）

> **板块职责**：按 S0 契约把**会话**沉淀为库内容。**只增不改历史**。
> **依赖**：S0（契约）· S1（落点）。**被依赖**：S3（维护链吃生产产物）。
> **证据**：【读码】`scheduler.ts:737` `registerDistill` · `distill*.ts` 15 件 ·【实测】审计。

---

## 1. 边界

| 是 | 不是 |
|---|---|
| 判定"这次会话值不值得沉淀" | ✗ 整合/提纯已有内容（S3） |
| 按契约产出基础数据（md + 环记录） | ✗ 决定"注入给谁"（S4） |
| 维护**蒸馏自身**的水位（会话区间游标） | ✗ 维护**深睡**水位（S3，虽同一状态机） |

**输入**：会话事件（`session/event` · `turn/end`）+ 转录
**输出**：md 投影（经 `record-shadow`）+ 环记录（经 `ring-commit`）+ 审计（`ledger.jsonl`）

## 3. 目标

### 3.1 契约驱动产出

```
会话事件 ──▶ 预筛（信号词，零成本跳过）
              │
              ▼
        蒸馏子代理（LLM 裁决：route / fclass / 候选）
              │
              ▼
        write_gate（宿主校验：契约 + 容量 + 形态）
              │
      ┌───────┴────────┐
      ▼                ▼
  md 投影          环记录
（成绩/画像/索引）  （decision/episode/commitment…）
  经 record-shadow   经 ring-commit
```

**新增约束**：`writeDispatch` 的**每一路输出**都必须在 S0 契约中有对应 `typeId`；无对应者的输出**直接拒绝**（而非静默写库）。⇒ 消除"产出了、无人能读"的再发生条件（当前 105 条环记录即此前例）。

### 3.2 两个待决

| # | 问题 | 建议 |
|---|---|---|
| **X6** | `episodes.jsonl` 孤儿 | **优先补生产者**（该数据含 `outcome` 成败信号，是 S4 效能估计的唯一现成样本源；退役则永久失去 257 条历史）⚠️ 需先评估与现有 `episode` kind 的关系（现 81 条 episode 从何而来） |
| **R1** | 助手侧读取 | 复核 §15.6 修复是否仍生效；建立**回归断言**（防再次丢失） |
