# UI1 · 面板架构整理方案（2026-09-15）

> **定位**：后端历经 S0–S4 + S4R/S4X/S4Y/S4Z（协议层 → 库核心 → 生产 → 维护 → 消费 → 环/记录/读侧/观测），
> **而 UI 侧自 S1–S4 重排后未做过架构级整理**。本方案一次性给出对齐决策。
>
> **配套验收**：`UI1-panel-architecture-acceptance.md`（**验收先出，再施工**）。
> **判因记录**：`UI1-adversarial-review.md` —— 本方案经对抗验证后**整篇重写**；
> 那份记录解释"为什么这版是这样"（含被否掉的三个方向），**不是本方案的补丁**。

## 1. 实测事实（全部为工具产出，非印象）

### 1.1 UI 规模（**node 精确解析**）

| 指标 | 实测 |
|---|---|
| `body.js` | **5477 行** |
| 函数定义 | **210 个**（含嵌套；**顶层（缩进 6）为 125 个声明 = 90 函数 + 35 `var`**） |
| **顶层符号**（缩进 6） | **125 个** = **90 个函数 + 35 个 `var`**（后者被**赋值 49 次**） |
| **高 fan-in 符号** | `UI` **34** · `Derive` **25** · `Cfg` **15** · `Log` **12** · `CSS` **8** · `refs` 7 · `inject` 6 · `Store`/`Fold`/`memoryViewScroll` 各 4 |
| **函数纯度** | 90 个顶层函数中，**69 个引用可变符号**，**仅 21 个是纯函数** |
| `render*` 函数 | **24 个**（互调 10 组，**仅 2 层深**） |
| 结构 | **全部包在一个手写 IIFE**（L15 – L5477 · 末行 `})();`），**内部含条件 CJS 导出**（`module.exports` ×2） |

> ⚠ **统计口径**：必须用 **node 解析**。PowerShell 的 `Get-Content`/正则对此文件给出过 **5117**（偏差 360 行）
> 与两次 **0** 的假值。**冻结基线若用错口径，门本身就是错的。**

### 1.2 UI 现有结构（**不是**"只有双画像+记忆"）

**6 个板块**：记忆板块（索引/候选/笔记/归档/统计）· 内容环 · 记录与图 · 观测（日志/错误/运维/指标）·
装配 · 认知环旋钮 + 设置（注入画像/记忆容量/模型向量/后台调度）。

**组件库覆盖已较全面**：`wa-tab-group` 8 · `wa-button` 7 · `wa-progress-bar` 5 · `wa-switch` 5 ·
`wa-select` 3 · `wa-icon` 1；且有**统一封装层**（`UI.button` 23 · `UI.select` 7 · `UI.tabs` 6）。

### 1.3 后端（供对齐）

**38 条 RPC 路由** · **19 个领域模块**（环 8 · 记录 2 · 读侧 3 · 观测 3 · 断言 2）。

### 1.4 **核心矛盾**

| 侧 | 纪律 | 状态 |
|---|---|---|
| 后端 `src/` | `check-module-growth`（冻结棘轮）· `audit-fnspan` · `audit-wiring` I1/I2 | ✅ 完备 —— 本轮多次被它拦下并**逼出领域接缝拆分** |
| 前端 `src-client/` | **无** | ❌ **一条都没有** ⇒ `body.js` 长到 **5477 行**而无人知 |

⇒ **这不是功能问题，是纪律不对等。** 加板块只会让单体更长。

### 1.5 门禁现状的两个约束（决定了下面的做法）

| 约束 | 实测 |
|---|---|
| `check-module-growth` **不能直接扩面** | 它**硬编码** `const SRC = join(root,'src')`，扫描面是 **`src/**/*.ts`**；而 `src-client/` 是 **`.js`** |
| 组件使用**不可静态全判** | `UI.button` 是 `body.js` 内 `var UI={}` 的方法，`wa-*` **运行时生成** ⇒ 静态只能看到字面量 |

### 1.6 回归证据的**覆盖边界**（决定要不要补证据）

`ui-geo-regress` 实测覆盖：弹窗/内容区/4 KPI 首屏/操作卡/**按钮由组件库承载**/**`shadowRoot` 存在**/
进度条接管方案值/**零 `wa-select` 残留**/下拉就位 · 且 **`.click()` 8 次**。

**但它不测**：`submit` = 0 · `fetch(` = 0 · `POST` = 0 ⇒ **不覆盖"提交 → RPC → 回流"**。

⇒ 仅凭它**不足以**证明"拆分后行为不变"，故方案含 **U5** 补齐。

## 2. 决策

### U0 · 让纪律可见（**必须先做**）

**为什么最先**：没有门，拆完会**长回去** —— 后端就是靠棘轮才被迫按接缝拆的。

| 卡 | 内容 |
|---|---|
| **U0-a** | **改** `check-module-growth.mjs`：支持**多扫描根**（`src/` + `src-client/`）且支持 **`.js`**；把 `body.js` **5477** 冻结为基线（棘轮，只许收紧） |
| **U0-b** | 新增 **`check-ui-components.mjs`**：**字面量对账** —— `vendor.js` 的 import ↔ 代码中的 `wa-*` 字面量，**两个方向都报**。**门内必须注明局限**：`UI.button`/`UI.select` 这类运行时生成的用法**扫不到**（不得声称"覆盖全部组件使用"） |
| **U0-c** | 新增 **`src-client/` 解析可读性**断言（防引入语法错误后静默）—— 现在连这一步都没有 |

### U1 · **按 fan-in 逐个抽服务**（**不做大 ctx 一次性迁移**）

**依据（node 实测 · 第二轮对抗）**：顶层 **125 个符号** = **90 函数 + 35 `var`**；这些 `var` 被**赋值 49 次**；
**90 个函数里 69 个引用可变符号**（只有 **21** 个纯函数可直接抽）。**高 fan-in 分布**：

| 符号 | fan-in | 性质 | 处置 |
|---|---|---|---|
| `UI` | **34** | 纯渲染封装 | **抽为 `ui-kit.js`** ⇒ 一次惠及 34 个函数 |
| `Derive` | **25** | 派生/格式化工具 | 抽为模块（只读） |
| `Cfg` | **15** | 配置读取 | 抽为模块（只读） |
| `Log` | **12** | 日志器 | 抽为模块（可注入） |
| `CSS` | **8** | 样式常量 | **只读常量**，最易抽 |
| `refs` · `inject` · `Store` · `Fold` · `memoryViewScroll` | 7/6/4/4/4 | **真·可变状态** | **留在入口**，按需以参数传给少数函数 |

**做法**：**按 fan-in 从大到小，一次抽一个**（`CSS` → `UI` → `Derive` → `Cfg` → `Log` …），
**每抽一个立即跑 `ui-geo-regress`**；**真状态留在入口**。

> ⚠ **为什么不是"先建一个大 ctx"**：那会**同时改动 69 个函数的签名** ⇒ 反馈周期长、回归面大，
> 与"小步可验"背道而驰（该判断由第二轮对抗实测得出，见判因记录 §6.1）。
>
> ⚠ **模块形态**：`body.js` 是**手写 IIFE**（末行 `})();`）且**内部含条件 CJS 导出**（`module.exports` ×2）
> ⇒ 拆成 ESM 时**包装形态要一并处理**（U2 需含此步）。

### U2 · 逐 `render*` 迁移（**执行单位是 24 个 render，不是 7 个 pane**）

**接缝 = 现有板块**（所以目标模块是 7 个），但**实际改动单位是 24 个 `render*`** —— 一次一个。
**迁移顺序遵拓扑**（互调 10 组、仅 2 层深）⇒ **自底向上**：先迁被调用者（`renderTogglesInject`…），再迁调用者（`renderViewToggles`）。

| 目标模块 | 收录的 render（示例） | 对应后端域 |
|---|---|---|
| `panes/memory.js` | `renderIndexRows` · `renderMemoryExpanded` · `renderNoteSections` · `renderSecNode` · `renderPersona` · `renderFacts` | 记忆库 |
| `panes/rings.js` | 内容环相关 render | `rings` / 各 `*-ring` |
| `panes/records.js` | 记录与图相关 render | `record-store` / `assertion-graph` |
| `panes/observe.js` | `renderViewObserve` · 日志/错误/运维/指标 | `event-envelope` / `audit-source` |
| `panes/assembly.js` | `renderSuite` | `suiteAssemblyMatrix` |
| `panes/mcl.js` | `renderMclKnobs` | `mcl` |
| `panes/settings.js` | `renderViewToggles` · `renderToggles*` · `renderConfigRaw` | `panel-config` |

**纪律**：每迁一个 ⇒ 跑 `ui-geo-regress` + **U5 行为证据** ⇒ 记录 `body.js` 行数 ⇒ **棘轮随之下调**。

### U3 · 核对既有判因（**不是**"推进组件库"）

🔴 **本卡方向经对抗验证**已从"推进 `wa-select`"**改为"核对判因"**：`ui-geo-regress` 明确断言
「**零 `wa-select` 残留**」且「下拉为原生实现……**已被像素级证据否决**」⇒ 那是**刻意的设计决策，且有门禁守着**。
**推进它会直接把门打红。**

| 卡 | 内容 |
|---|---|
| **U3-a** | 核对判因**是否仍有效**（上游 `wa-icon` 能否正确绘制箭头）；结论**写入文档**，不擅改实现 |
| **U3-b** | 把该判因从**注释**提升为**可机检说明**（现状只以 `ui-geo-regress` 断言形式存在，读码者不易发现） |

### U5 · 补行为级证据（**补 §1.6 的缺口**）

| 卡 | 内容 |
|---|---|
| **U5-a** | **一条 `/save` 端到端**：请求 → 200 → **数据回流且 DOM 更新**（`test-route-schema` 只覆盖了"400 不入 handler"） |
| **U5-b** | 拆分前后**同一次提交的 DOM 差异为空**（施工前先存基线） |
| **U5-c** | **反例自证**：故意断一条回流 ⇒ U5 必须红（否则该证据无效） |

## 3. 施工顺序（依赖决定，不可乱序）

```
U0  让纪律可见（改门 + 两新增）   ← 先红：应报 body.js 5477 超基线
     ↓
U1  ui-kit.js + ctx.js（打破闭包）  ← 没有 ctx.js，U2 不可开工
     ↓
U2  24 个 render* 逐个迁移（→ 7 模块）
     ├─ 每迁一个：ui-geo-regress + U5
     └─ 棘轮逐卡下调（5477 → … → < 800）
     ↓
U3  核对 wa-select 判因（写文档，不擅改实现）
     ↓
U5  贯穿 U1/U2 全程（行为证据）
```

## 4. 非目标（明确不做）

- **不新增功能板块** —— 本轮是**架构整理**。
- **不改视觉设计** —— 皮肤/令牌/布局**维持现状**（S1 已定，`check-layout-px` 守）。
- **不引新组件库** —— 沿用 Web Awesome（`AGENTS.md` 规则 5：**不从零造轮子**）。
- **不与门禁对抗** —— 凡与现有断言冲突的方向**一律不做**（U3 即此例）。

## 5. 预期结果（可量化，验收时核对）

| 指标 | 现状 | 目标 |
|---|---|---|
| `body.js` 行数 | **5477** | **< 800** |
| 顶层符号 | **125**（90 函数 + 35 `var`） | 服务全部抽出；**35 个 `var` 里仅真状态留在入口** |
