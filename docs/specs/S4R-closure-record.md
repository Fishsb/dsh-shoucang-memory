## ⚠ 本卡最重要的发现：**「部署」≠「热重载」**（假绿的第四层）

**现象**：R1 改完后首次对拍 **FAIL（3/3）**，差异是多出 `【守藏·三层判据】` 块 —— 那是 **S4-2** 的产物，
**不是 R1 引入的**。

**根因**：S4-2 轮我做了 `npm run build` + `deploy-installed.mjs`，**但从未 `dev_reload_package`** ⇒
**运行中的插件一直跑着旧代码**，直到本卡首次热重载才加载。所以我落的第一份基线是**旧代码输出**，
**无法用于验证 R1**（它混淆了"S4-2 的累积变化"与"R1 的变化"）。

**这补全了「仓内绿 ≠ 运行态绿」的层级**：

| 层 | 判据 | 本轮教训 |
|---|---|---|
| ① 仓内绿 | typecheck / build / check-runner | 早已有 |
| ② 部署同步 | `check-installed-sync --strict` 0 漂移 | 早已有 |
| **③ 运行态生效** | **必须显式 `dev_reload_package`** | ⚠ **本卡新增认知**：`deploy` 只同步文件，**进程仍持旧模块** |
| ④ 功能探针 | 端点真响应且内容正确 | 早已有 |

**处置（本卡已执行）**：回退 R1 → build + deploy + **reload** → 落基线 → 恢复 R1 → build + deploy + **reload** → 对拍 ⇒ PASS。
**并已把「改 src 后必须 reload 才验」写进本记录**（避免下次再混淆）。

## R2 · 账转真 + 裁切归位 —— ✅ 完成

### 关键判因（决定走哪条路）

B2 的断言是「**账与真实裁切可比**」，**不是**"裁切必须由装配器执行"。⇒ 两条路：
**(a)** 主路径改调 `assembleSupply`（改裁切行为 ⇒ 注入内容会变，**风险高**）；
**(b)** 让账**吃主路径自己的裁切结果**（不改行为）。
⇒ **选 (b)**：风险低，且直接命中断言。（原方案默认 (a)，是被断言的字面读法误导。）

### 三步走（每步独立对拍验证）

| 步 | 改动 | 注入文本对拍 |
|---|---|---|
| 1 | `clampLines` 返回**被丢的行**（原先只返回个数）—— 裁切行为不变 | ✅ 三 case 逐字节一致 |
| 2 | 账改吃真实值（`real` 参数 + `cache.realCut` + 提升 `m`/`droppedMem` 到外层） | ✅ 逐字节一致 |
| 3 | 修 `droppedStable = 0` 的**少算** | ⏸ **未做** ⇒ 见遗留 **L8**（它会改注入文本，须单独决策） |

### 逐条验收（B1–B4）

| # | 断言 | 实测 |
|---|---|---|
| **B1** | `kept` 与注入文本**互核** | ✅ `- ` 行 **42** == `kept.stable 35` + `kept.dynamic 9` − **2**（两个画像块标题） |
| **B2** | `droppedRows` = 真实被丢**内容**（逐条可比） | ✅ 逐条非空；且**被丢的行确实不在注入文本中**（泄漏 **0**） |
| **B3** | 反例自证：账与装配器口径**故意可不同** | ✅ **6 条 vs 1 条** —— 若 R2 未生效，二者会同源而恒等 |
| **B4** | 账是算出来的（非常量） | ✅ 换查询后 `dynamic` **3 vs 9** |

### 最有说服力的一个数

```
装配器口径 dropped     = 6 条     ← 旧账（近似值）看到的
主路径真实 droppedRows = 1 条     ← 实际只丢了 1 条
```

⇒ **旧账虚报了 5 条丢弃**。"账是近似值"不是措辞谨慎，而是**可量化的偏差**。

### 一次领域归位（顺带解冻棘轮）

改动使 `panel-shared` 达 **793 > 790**（冻结上限）⇒ 门禁报"出路二选一"。
按**出路①（按领域接缝拆）**处置：把 `clampLines` 迁至 **`supply-assembly`** ——
它是**裁切**，与 `budgetOf` / `assembleSupply` 同域，**放在 panel 侧本就是错位**。
⇒ `panel-shared` **793 → 775**（重回基线内），且归位本身是架构改善。

### 一处口径陷阱（值得记下）

B1 首次断言 `dash == kept.stable + kept.dynamic` **不等（42 vs 44）**。查因：`kept.stable` 计的是

**不是代码错，是我的断言口径错** —— 已把该口径写进 `supplyUsageMeta` 的头注（防后人重踩）。

## R3 · D2 判据重定 —— ✅ 完成（**C1/C2 达成；C3 按规 SKIP**）

### 关键判因

原 S4-7「两条件分流」的判据是**写死**的，其前提"瓶颈在标签门"**已被 S1 实测证伪**
（真实瓶颈是**召回零命中 81.7%**，1411 步双源；被标签门挡下的 337 条里 **279 条是"(无/空)"**）。
⇒ 写死的判据会把人引向"调阈值"，而**调阈值对召回层无效**。故判据必须**从数据自己得出结论**。

### 交付

| 产物 | 内容 |
|---|---|
| `recall-diagnosis#adviseFromMissCounts` | 由 `missReason` **分布**推导调参方向：`insufficient-data` / `enable-embed` / `fix-recall` / `lower-threshold`；带 `why`（**可见化**，不静默） |
| `scripts/recall-diagnose.mjs` | 接入该判据 ⇒ 诊断输出末尾直接给**建议与依据** |
| `scripts/test-recall-advice.mjs`（新，14 条） | C1 四分支 + **C2 反例自证** + 边界稳健 |

### 逐条验收（C1–C3）

| # | 断言 | 实测 |
|---|---|---|
| **C1** | 判据**由数据推导**，可被诊断输出驱动 | ✅ 四分支各自可达；`recall-diagnose` 已接入并输出建议 |
| **C2** | **反例自证**：两组分布 ⇒ 不同结论 | ✅ 同总量同未命中数（100/60）下：召回层主导 ⇒ `fix-recall`，阈值层主导 ⇒ `lower-threshold` —— **判据有区分力，非恒真** |
| **C3** | 数据不足 ⇒ **如实标注，不伪造** | ✅ 真样本 **0 条** ⇒ 输出 `insufficient-data`（"样本 0 < 下限 30 ⇒ **不猜方向**"）。本卡**判 SKIP** 而非 PASS |

**边界稳健**（一并断言）：零样本 / 全命中（`miss=0` 不除零）/ 负数钳 0 / `minSamples` 闭区间。

### 复验方法（C3 交付物 —— 数据到位后照此执行）

```bash
node scripts/recall-diagnose.mjs     # 输出归因分布 + 🧭 建议（由数据推导）
```
- **期望形态**：`可归因 > 30` 后，`advice` 落 `fix-recall` / `lower-threshold` / `enable-embed` 三者之一；
- **判读**：若 `fix-recall` ⇒ **不要调阈值**，应查词表/索引/情境；若 `lower-threshold` ⇒ 才可调 `mclFamiliarThreshold`。
