# S4R · 收尾方案：渲染等价化接管（2026-09-14）

> **定位**：**不是新板块**，是 S4 的收尾深化。解决 S4 验收中三项 `⛔ 经决策不采纳`（B2/B3/B4）的**真实根因**。
> 配套验收：`S4R-closure-acceptance.md`（**先出验收，再施工** —— 本次按用户要求）。
> 依赖：S0–S4 全部已交付；`docs/specs/S4-acceptance-record.md` §6.1 的双侧实证对照是本方案的输入。

---

## 1. 问题（不是"要不要切换"，而是"为什么会有两套"）

现状**同时存在两套渲染实现**：

| | 主路径 `buildHotMemoryText`（`panel-shared`） | 装配器 `renderSupplyText`（`supply-assembly`） |
|---|---|---|
| 作用 | **实际注入文本** | 影子账（`usage`）用 |
| 抬头行 | 有（含 `memRoot` 与 `get_file` 指引） | 无 |
| 块标题 | `agent 画像（AGENT.md…）` / `用户画像（USER.md）` | `【核心】`/`【恒定面】`/… |
| 行前缀 | 自动补 `- ` | 不加 |
| 段序 | oneshot → stable → dynamic | core → stable → dynamic → oneshot |
| 省略文案 | **逐块** | 只给总数，缺省不产 |

⇒ 直接后果：`usage.kept/dropped` 只是"**同批候选按装配器口径重算**"，**不可当作主路径实际保留了哪些行**（B2 未达成）。

**这不是"装配器能力不足"** —— 我上一轮（S4 §6.1）就是按"能力不足+须产品决策"处理的。**那是误判**：
`renderSupplyText` 的 `RenderOpts` 只有 `headers` 与 `annotateOverflow` —— **缺 4 项渲染维度**，
所以"逐字节等价已被证伪"证的不是"不可能"，而是"**选项不全**"。

---

## 2. 根因（一句话）

> **渲染没有单一实现**：选行/裁切/渲染三件事里，"渲染"被写了两遍，且两遍的可配维度不同。

按 **[认知] 架构优先** 的判据：说不出承载节点的改动即局部补丁 —— 本项的承载节点很明确：
**`renderSupplyText` 应当是唯一渲染器**，主路径应向它收敛（而不是反过来给影子账打补丁）。

---

## 3. 解法（架构级，非补丁）

### 3.1 把渲染收成单一实现

扩展 `RenderOpts`（**增量扩展，不整组重写** —— 既有调用方零影响）：

```ts
export interface RenderOpts {
  headers?: Partial<Record<Seg, string>>        // 既有
  annotateOverflow?: boolean                    // 既有
  /** R1 新：段序（缺省 = 装配优先级）。主路径传 ['oneshot','stable','dynamic'] */
  order?: readonly Seg[]
  /** R1 新：抬头行（缺省无）。主路径传 `[守藏·热记忆] …：` */
  leadLine?: string
  /** R1 新：行前缀补全（如 '-'）：不以该前缀开头的行自动补 */
  linePrefix?: string
  /** R1 新：逐块省略文案模板（含 `{n}` 占位）—— 替代装配器现在的"只给总数" */
  overflowNotes?: Partial<Record<Seg, string>>
}
```

**关键洞察（使等价成为可能）**：装配器的 `blocks.stable` 是**一个字符串**，其**内部结构由调用方拼好**
（agent 块 + user 块 + 各自标题）。⇒ 渲染器**不必知道** stable 内部有两块，
只需按 `headers.stable` 渲染外层、按 `overflowNotes.stable` 出省略行。

### 3.2 主路径收敛（两步，可分别回滚）

1. **R1（渲染收敛）**：主路径的**文本拼接**改调 `renderSupplyText`（选行/裁切逻辑暂不动）⇒ 文本**逐字节不变**
2. **R2（裁切收敛）**：主路径的**裁切**改由 `assembleSupply` 执行（替代手写 `clampLines` 组合）
   ⇒ `usage` 从"近似值"变为**真实结果**（B2 转绿）

**分两步的理由**：R1 只动渲染（风险可控、可逐字节验证）；R2 动裁切语义（风险高）。
两者**各自有独立验收与回滚**，不混在一次改动里。

### 3.3 关键纪律：**先让断言变红**

按成长画像那条 **[原则]**（修动前先加断言让旧行为变红以实证缺陷，改后转绿）：
R1 的第一步**不是**改代码，而是写 `scripts/test-render-equivalence.mjs` ——
给定固定候选集与固定预算，断言「新路径输出 == 现行主路径输出」。

**预期首跑必红**（因为两套渲染现在不同）。红 → 说明断言**真的在测那件事** → 再改造到绿。
若首跑就绿，说明断言没测到差异，须收窄。

## 5. 风险与回滚

| 风险 | 处置 |
|---|---|
| 改渲染致**注入文本走样**（违反用户偏好） | **R1 的验收核心就是"逐字节不变"**；不绿不合入。且 `linePrefix`/`leadLine` 等**缺省值 = 保持装配器现有行为**，只有主路径显式传参才变 |
| 改裁切致**注入内容变化** | R2 单独一卡；先比对"裁切前后 kept/dropped 是否一致"，不一致即停（说明两套算法真有语义差，须逐项决策） |
| `panel-shared` 冻结棘轮（764/779） | R1/R2 都是**替换调用**（净增极小）；若超限，按 L5 先例继续按领域接缝拆 |
| 共享 `RenderOpts` 被多处使用 | **增量扩展**：新字段全可选、缺省=现行为 ⇒ 既有调用方**零影响**（由 `check-*` + 既有测试守） |
| 备份 | 动手前 `Copy-Item` 备份 `panel-shared.ts` 与 `supply-assembly.ts`（[原则] 变更先判因备份） |
