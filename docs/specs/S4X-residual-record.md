## X1 · 修 L8（`droppedStable` 少算）—— ✅ 完成

### 缺陷

`panel-shared` 中 `const droppedStable = 0` 是**硬编码**，而 stable 段实际会丢
`dA.length + dU.length` 行（55%/45% 分块裁切）⇒ 末尾「本步受预算 N 字符约束省略 **M** 行」的 **M 少算**。

### ⚠ 关键前置发现：它是**条件缺陷**，不是"当前就在错"

实测：缺省配置（`budgetChars=4000` ⇒ `capStable≈3200`）下画像仅占 ≈1990 字符 ⇒ **stable 从不触发裁切**
⇒ `dA=dU=0` ⇒ 硬编码 `0` **恰好正确**。
⇒ **必须构造场景才能实证**（这也是它长期未被发现的原因）。构造方式：临时把注册表预算降到 **1200**
（⇒ `capStable≈960` < 1990），并**重新生成 + 构建 + 部署 + 热重载**
（⚠ 不重载则运行态仍是旧代码 —— S4R/R1 的教训）。

### B2 决策与理由（逐条可检验）

**`runDeepSleep` → 不拆**（**硬约束，非偏好**）：
1. 它是**顺序流水线**，而各阶段共享函数开头的 **约 20 个解构别名**
   （`ctx` / `log` / `audit` / `ledger` / `kRoot` / `config` / `llmState` / `capEnv` / `streak` /
   `traceSince` / `runNode` / `validateProvider` / `resolveLlm` / `resolveDefaultModel` / `pickParent` / …）；
2. 抽出阶段函数 ⇒ 必须传一个**大依赖包** ⇒ **撞 `audit-wiring` I2（Deps ≤12 字段）棘轮**；
3. 要拆，得**先重构依赖传递方式**（把别名收进一个 context 对象）—— 那是**架构改动**，
   远超"L2 行数"的范围，且会动到**已验收**的深睡主流程；
4. `audit-fnspan` 是**报告态** ⇒ 无门禁压力，不构成"必须拆"的理由。

**`gatherMaterials` → 不拆**（**收益检验**）：
1. 它的 11 段**已经用 IIFE 分段**，且每段前有**判因注释**（= 段名 + 为什么这么取）⇒ 可读性已达标；
2. **每段都只被调用一次** ⇒ 抽成模块级函数**不增任何复用**，只把"局部性"打散（读者需在文件内跳 11 处）；
3. 它**能拆**（只吃 `root`，不撞 I2）—— 即本项不是"做不到"，而是"**收益不抵散裂**"；
4. **判据留给未来**：若某段出现**第二个调用方**（如诊断脚本要复用 `readForgetCandidates`）或需要独立单测，
   **那时再拆** —— 判据是"**出现第二个调用方**"，不是行数。
