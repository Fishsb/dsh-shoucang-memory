## 3. 本轮修的真实缺陷：`replayRecent` 的**口径不符**

**材料头注自称**：「近 7 日已有条目被再次命中 …… 供深睡判「**跨日**二次激活」（replay / dream-lag）」。

**而实现**：只把命中**次数**累加排序：

```ts
const cnt = new Map<string, number>()          // 旧实现：只数次数
top = [...cnt.entries()].sort((a,b)=>b[1]-a[1]).slice(0,10)
```

⇒ **"同一天读了 100 次"会盖过"跨 3 天各读 1 次"** —— 而后者才是 replay 的语义。

**实测（2026-09-14）**：近 7 日 **41 条**真跨日；旧口径 top-10 **恰好全跨 5 天**（**碰巧**，非保证）。
⇒ 属**条件缺陷**（与 L8 同性质）：当前数据下看不出，换个分布就错。

**修正**（按**不同日期数**降序，`≥2` 天才算跨日，并把跨日数**显式写进材料**）：

```ts
const days = new Map<string, Set<string>>()    // 新实现：按日期去重
top = [...cnt.keys()].filter((k) => (days.get(k)?.size ?? 0) >= 2)
  .sort((a,b) => (days.get(b)!.size - days.get(a)!.size) || (cnt.get(b)! - cnt.get(a)!)).slice(0,10)
// 输出：`env.md §DSH 环境（跨 5 天 · 55 次）`
```

**验证**：新输出 `env.md §DSH 环境（跨 5 天 · 55 次）` ⇒ 深睡**可据此判"二次激活"**（此前只有次数，无跨日维度）。

## 9. 修正 `inject-baseline-diff` 的设计缺陷：**它把"记忆库是活的"当成了失败**

**现象**：本门（S4R/R0 引入）在深睡产出 3 条原则后**假红 3/3**；我更新基线后，**又因新增原则再次假红**。

**根因**：我把判据写成 **raw 文本逐字节相等**。而**记忆库是活的** —— 深睡、蒸馏、其他会话**持续写**
⇒ 注入面（画像段 / 索引段）**必然随之变**。⇒ 该门在活跃系统里会**频繁假红**，
最终被人静音 —— **那就等于没有**。

**修正**：比对前归一化 —— `- ` 开头的行是**记忆条目**，替换为 `- <row>` 占位；其余行（抬头 / 段标题 /
省略提示 / 三层判据块 / 情境块）**原样比对**。⇒ **记忆增删不报**，而**结构 / 格式 / 顺序 / 裁切提示**
的任何变化**仍会抓到** —— 后者才是本门该守的（`- ` 行本来就是活的）。

```js
const normalize = (t) => t.split('\n').map((l) => (/^-\s/.test(l) ? '- <row>' : l)).join('\n')
// 判据：normalize(基线) === normalize(当前)；raw sha 仍打印（内容变了就如实显示，但**不算失败**）
```

**验证**：修正后三 case `✅ 骨架 … vs …` ⇒ PASS；且输出会明确标注「**内容已变**：记忆库是活的，不算失败」。

> **为什么这个修正值得单独记**：一个**会把正常现象判成失败**的门，比**没有门**更糟 ——
> 它会训练人"看到红灯就忽略"。这与 §1 的教训同族：**判据必须对准它真正要守的东西**。
