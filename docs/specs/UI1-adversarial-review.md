# UI1 · 对抗验证报告（2026-09-15）

> **任务**：对 `UI1-panel-architecture-plan.md` 做**对抗性审查** —— 主动找它的漏洞，而非复述它。
> **方法**：先列"方案最可能错的点"，再**逐条实测**（[原则] 结果验证重实证：对抗不靠推理）。
> **结论**：**4 处实质错误**，其中 1 处**与现行门禁直接冲突**；1 处数字错误。方案已按下述修正。

## 二🔴 **与现行门禁直接冲突**（本轮最严重的发现）

`ui-geo-regress` 的两条断言：

```
· 零 wa-select 残留（二度回滚彻底；判因见源码注释）
· 下拉为原生实现（其箭头由原生控件绘制；WA select 的箭头未渲染已被像素级证据否决）
```

⇒ **`wa-select` 不是"待推进"，而是"已用像素级证据判定不用，且有门禁守着"**。
⇒ 方案 **U3-1（"`wa-icon` 已 import ⇒ 约束解除，可推进 `wa-select`"）是错的** ——
   那是**从"依赖已解除"推断"可以推进"**，而事实是**刻意的设计决策**。**照方案做会把门打红。**

## 四、修正后的方案（取代原 U0–U3）

### U0（修正）· 不是"扩面"，而是**改门 + 两处新增**

- **U0-a′**：改 `check-module-growth.mjs` —— 扫描根支持**多根**（`src/` + `src-client/`）且**支持 `.js`**。
  **先红验证**：改完首跑必须报 `body.js 5477 > 基线`（**不红即说明改动没生效**）。
- **U0-b′**：组件门**降级为"字面量一致性"**（扫 `wa-*` 字面量与 `vendor.js` import 对账），
  **并在门内注明局限**：`UI.button` 这类**运行时生成**的用法**扫不到**（现状：静态可判者仅部分）。
- **U0-c（原缺失）**：**`src-client/` 需要有 `.js` 的语法/规模基线** —— 现在**连 lint 都没有**。

### U1（修正）· 先建**上下文层**，再谈拆模块

原方案说"抽 `ui-kit.js`（`UI.*` 先独立）"—— **不够**。实测有 **98 个顶层符号**，
故真正要抽的是**两件**：

1. **`ui-kit.js`**：`UI.*`（纯渲染元件，无状态）—— **可干净抽出** ✓
2. **`ctx.js`**（新）：把 `api`/`Store`/`Log`/`Cfg`/`Fold`/`Derive`/`status`/`Bus`… 收进**一个显式上下文对象**，
   pane 以**参数**接收 ⇒ 这是**唯一能打破 IIFE 闭包**而不造全局的办法。

**这一步是新增的，且是 U2 的前置** —— 原方案缺它，故 U2 不可直接开工。

### U2（修正）· 接缝是 **31 个 `render*`**，不是 7 个 pane

- 逐 `render*` 迁移（31 个），**落到对应的 7 个 pane 模块**里；
- **每迁一个**跑 `ui-geo-regress`（100 PASS）+ 记录 `body.js` 行数；
- **行数棘轮逐卡下调**（与后端 `panel-shared` 847→765 同一套流程）。

### U3（**删除并改写**）· 组件库"最后一公里"**不成立**

- **删除**"推进 `wa-select`" —— 与门禁冲突，且已有像素级判因。
- **改写为**：**核对判因是否仍有效**（若 `wa-icon` 升级到能正确绘制箭头，再议），
  并**把该判因从注释提升为可机检的说明**（现状只在 `ui-geo-regress` 里以断言形式存在）。

### 新增 U5 · **补行为级证据**（因为 F 项发现证据链有缺口）

`ui-geo-regress` **不测提交链路** ⇒ 拆分的"行为不变"缺一环。补：

- **U5-1**：至少一条 **`/save` 端到端**（`test-route-schema` 已覆盖"400 不入 handler"，但**未覆盖正常路径回流**）；
- **U5-2**：**契约覆盖不变**（`check-panel-contract` 已有）+ **一条真实提交的 DOM 前后对比**。

### 6.1 🔴 第二轮最重要的结论：U1 的**风险模型错了**

方案把 U1 描述为"**打破闭包（前置一步）**"。实测表明它是：

```
35 个可变符号（含 module/exports/BASE/inject/CONTRACT/ICONS/CSS/Bus/Store/Log/Prog/Cfg…）
被赋值 49 次
90 个顶层函数里 69 个引用可变符号
高 fan-in：UI(34) · Derive(25) · Cfg(15) · Log(12) · CSS(8) · refs(7) · inject(6) · Store(4) · Fold(4)
```

⇒ **"先建一个大 ctx 再一次迁移"会同时改动 69 个函数的签名** —— 反馈周期长、回归面大、**与"小步可验"背道而驰**。

### 6.2 实测同时给出了**更低风险的路径**（本轮真正的产出）

关键区分：那 9 个高 fan-in 符号里，**前 4 个是"服务/工具"而非状态**：

| 符号 | fan-in | 性质 | 处置 |
|---|---|---|---|
| `UI` | 34 | **纯渲染封装** | ⇒ **就是 `ui-kit.js` 要抽的东西**：抽它 ⇒ **一次惠及 34 个函数** |
| `Derive` | 25 | 派生/格式化工具 | 抽为模块，**只读** |
| `Cfg` | 15 | 配置读取 | 抽为模块，**只读** |
| `Log` | 12 | 日志器 | 抽为模块（**可注入**） |
| `CSS` | 8 | 样式常量 | **只读常量**，最易抽 |
| `refs` · `inject` · `Store` · `Fold` · `memoryViewScroll` | 7/6/4/4/4 | **真·可变状态** | **留在入口**，按需以参数传给少数函数 |

⇒ **修正后的 U1 = 按 fan-in 从大到小逐个抽服务**（`CSS` → `UI` → `Derive` → `Cfg` → `Log` …），
**每抽一个立即跑 `ui-geo-regress`**；**真状态留在入口**。**不做大 ctx 一次性迁移。**

### 6.3 模块形态（新发现，影响拆法）

`body.js` 是**手写 IIFE**（首行注释 + 末行 `})();`），且**内部含 `module.exports` / `exports.` 各 2 处**
（**条件 CJS 导出**，非 esbuild 产物：`esbuild`/`__toCommonJS` 命中均为 0）。
⇒ 拆成 ESM 时**包装形态要一并处理**（方案 U2 需明确这一点）。
