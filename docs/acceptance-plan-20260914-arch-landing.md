## 0. 验收总则

### 0.1 一句话口径

**任一条验收项红 ⇒ 该阶段未完成。** 不存在"基本完成""大体达标"。
允许的例外只有一种：已**显式登记为 xfail** 的已知未修项（须在报告里点名，不得隐藏）。

### 0.2 三条纪律（缺一条，验收结论即不可信）

1. **结论与证据同源**：每条结论必须附「同一次读取」的证据（路径 + 行号/字节 + 时间）。
   禁止用昨天的读数支撑今天的结论。
2. **否定结论前先列全变体**：说"某函数没被调用"之前，必须把 `export const` / `export function` /
   `export async function` 等所有导出形态都搜过。
3. **反向证伪不可省**：任何新增门禁，必须制造一次违规证明它会红。
   **只证明"绿"不证明"会红"的门禁 = 未验证**——它可能只是永远绿。

### 0.3 关键提醒：「仓内绿」≠「运行态绿」

测试全绿只说明仓库内自洽。**必须**另跑已安装副本校验与特性探针，否则会出现
"修复已提交、编译已通过、但宿主加载的仍是旧代"而三道门全绿的情况（本仓有过先例）。

## 2. 阶段 0 验收 · 防堆叠门禁底座

### 2.1 应交付

两件机检，均带 `--selftest`，且**都已登记进 `scripts/check-runner.mjs` 的 `CHECKS`**
（未登记 = 等于没写，本仓有三次前例）。

### 2.2 逐项判据

#### A. 大模块冻结（`check-module-growth`）

| 判据 | 通过标准 | 怎么验 |
|---|---|---|
| 存在硬顶 | 任何非生成物模块超过硬顶即红 | 构造一个超顶模块 ⇒ 必须 FAIL |
| 存在冻结名单 | ≥阈值行数的模块**登记基线**，超出「基线 + 容差」即红 | 构造超基线且超容差 ⇒ 必须 FAIL |
| **容差真的生效** | 超基线但在容差内 ⇒ **不红** | 构造 +容差内 ⇒ 必须 PASS（这条防"名义有容差、实际一超就红"） |
| 容差不是额度 | 容差内必须**打印提示** | 检查输出含提示文案 |
| 新增大模块不许无声混入 | 出现新的 ≥阈值模块而未登记 ⇒ 红 | 构造新大模块 ⇒ 必须 FAIL |
| 幽灵基线要清理 | 基线表里有而源码中没有的条目 ⇒ 红 | 构造幽灵条目 ⇒ 必须 FAIL |
| **生成物必须排除** | `*.generated.ts` 不参与冻结与硬顶 | 检查扫描面声明，且生成物不计入 |

#### B. 跨域「文件即通道」契约（`check-file-channel`）

| 判据 | 通过标准 | 怎么验 |
|---|---|---|
| **方向一：登记 ⟶ 代码** | 登记的每个写/读侧模块，源码里必须还能找到该介质标识 | 改掉某登记模块里的介质名 ⇒ 必须 FAIL |
| **方向二：代码 ⟶ 登记** | 源码里**实际引用**该介质的模块集合必须 ⊆ 登记表 | 新增一个未登记的引用者 ⇒ 必须 FAIL |
| 常量别名也算引用 | 通道若在读写侧只引用常量（不写字面量），必须能识别 | 用常量名引用 ⇒ 必须 PASS |
| 显式豁免需理由 | `mentions` 类豁免必须逐条写理由 | 检查登记表结构 |
| 注释不算引用 | 注释里的提及不得被判成引用 | 只在注释里提及 ⇒ 必须 PASS |

> **A/B 的关键验收动作**：不看实现，只跑 `--selftest`，确认它输出**多条**正反例且全过。
> 只有一条"完全一致 ⇒ 无错"的 selftest 等于没测。

### 2.3 阶段 0 完成判据

- 两件机检均在 `CHECKS` 中（含 selftest 变体）
- `--selftest` 覆盖：正向、方向一红、方向二红、豁免、注释、别名、容差内、超容差、幽灵、未登记
- §7 的两条反向证伪均已执行

## 3. 阶段 1 验收 · 隐式通道显式化

### 3.1 应交付

上游产线介质签名接入注入侧稳定面缓存键 + `invalidate()` 缺陷修复。

### 3.2 判据

| # | 判据 | 通过标准 | 怎么验 |
|---|---|---|---|
| 1 | **签名覆盖三条介质** | `activity.jsonl` / `warm-recall.json` / `delta.md` 任一尺寸变化都会改变缓存键 | 单测：改介质尺寸 ⇒ 键变化 |
| 2 | **不含无关介质** | 不得把与稳定面无关的介质（如 `records.jsonl`）签进去——签了只会平白增加失效次数 | 读登记/实现，确认覆盖集合有理由 |
| 3 | **零耦合** | **不得**让产线侧回调注入侧（不得重造跨域通道） | 检查产线侧是否 import/调用注入侧；应为"只写文件" |
| 4 | **零抛出** | 介质缺席 / 读取失败 ⇒ 回落占位值，**不得影响注入** | 单测：删掉介质文件 ⇒ 不抛、注入仍产出 |
| 5 | **`invalidate()` 覆盖完整** | 必须同时清 **query 缓存** 与 **稳定面缓存** | 单测：调 `invalidate()` 后，稳定面必须重算（**不能只清一个**） |

> 第 5 条是本阶段最容易漏的一条：只清 query 缓存、不清稳定面缓存，症状是
> 「面板写入后画像段沿用旧值至多 120s」——**通道建了、通知只做了一半**。

## 4. 阶段 2 验收 · 产线流程实例

### 4.1 应交付

水位行**纯增量**扩展 `runId` / `phase` / `attempt`；新增读回接口；关键阶段（尤其 spawn 前）落 phase。

### 4.2 判据（**兼容性是本阶段唯一不能靠"看着对"的部分**）

| # | 判据 | 通过标准 | 怎么验 |
|---|---|---|---|
| 1 | **旧行可读** | 磁盘上历史水位行（无新字段）必须能读，且 phase 回落为**中性值**（不得判成"运行中"） | 单测：喂一条旧格式行 |
| 2 | **不传 run 时逐字段等同旧格式** | 不得偷偷改变既有写入点的行为 | 单测：逐字段断言**不出现**新字段 |
| 3 | **`attempt` 可选** | 不传则不得出现该字段 | 单测：字段存在性断言 |
| 4 | **既有字段语义不变** | `sessionId` / `lastSeq` / `type` 一字不改 | 单测 + 读 diff |
| 5 | **崩溃在 spawn 时续传边界不变** | spawn 前落的那条**不得推进** `lastSeq` | 单测：写"段完成(100)"→"spawn(100)"→ 读回 lastSeq 必须仍是 100 |
| 6 | **能看出卡在 spawn** | 崩溃场景下读回 phase 应为 `spawn` | 单测：同上场景断言 phase |
| 7 | **口径与既有读链一致** | 新读回接口取"末行"的规则必须与既有水位读链**同口径** | 单测：同一文件两种读法结果一致 |
| 8 | 无文件 / 无该会话 | 返回空值且**不抛** | 单测 |

> 第 5 条是本阶段**唯一可能引入回归**的地方：多写了一条同 seq 的水位行，
> 若它改变了"末行生效"的结果，续传就错位了。**必须单测钉死。**

### 4.3 深睡侧（若一并做）

- 若**未做**：必须在交付记录里写明理由（深睡状态是内存态，与蒸馏不同构；贸然落盘 = 新增一条流，
  与"多流合并"目标相悖），且**不得**留下半成品。
- 若**已做**：按 4.2 同规格验收（旧格式兼容 + 崩溃续传边界）。

### 4.4 阶段 2 完成判据

- 新增单测文件已登记进 `CHECKS`
- 既有水位守卫类测试（`test-watermark-guard`）保持绿

## 5. 阶段 3 验收 · 读侧装配器接管主路径

> ⚠ 本阶段**验收口径取决于先定的方向**，两种方向的判据完全不同。**先确认方向，再验。**

### 5.1 若采用「A · 保持现状 + 显式登记」

| # | 判据 | 通过标准 | 怎么验 |
|---|---|---|---|
| 1 | **主路径一字未动** | 注入文本生成路径的产出**逐字节不变** | 与改动前基线比对（若已无基线，以代码 diff 为准：主路径函数体不得有语义改动） |
| 2 | **近似性已显式声明** | 代码注释里必须写明"影子账是近似值，不可当作主路径实际保留行" | 读注释 |
| 3 | **不得静默切换** | 注释须写明"若将来接管，必须先做产品决策" | 读注释 |
| 4 | 五处结构差异已登记 | 抬头行 / 块标题 / 行前缀 / 段落顺序 / 省略文案，差异清单在文档中可查 | 读文档 |

**A 的验收本质是"没改"**——因此最重要的一条是**证明主路径没变**，而不是证明新功能可用。

### 5.2 若采用「B · 受控变更」

| # | 判据 | 通过标准 | 怎么验 |
|---|---|---|---|
| 1 | **对比测试先行** | 必须有「主路径 vs 装配器」的对比测试件，且已登记 | 检查文件存在 + 在 `CHECKS` 中 |
| 2 | **文本变更被明确接受** | 五处差异要么已对齐、要么已被用户书面接受 | 用户确认记录 |
| 3 | **KPI 与影子账重新校准** | 旧账与新账不可比，必须重新建立基线 | 检查校准记录 |
| 4 | **CHANGELOG 标注** | 用户可感知（注入文本变化）必须记入 `[Unreleased]` | 读 CHANGELOG |
| 5 | 渲染级证据 | §1 ④ 通过 | 同 §1 |

### 5.3 阶段 3 完成判据

- 方向已明确（A 或 B），且**只满足对应方向的判据**（不许混用）
- 若选 A：主路径零改动 + 近似性声明到位
- 若选 B：用户验收文本 + 重新校准 + CHANGELOG

## 6. 阶段 4 验收 · 拆大模块

### 6.1 判据

| # | 判据 | 通过标准 | 怎么验 |
|---|---|---|---|
| 1 | **按接缝拆，不按行数切** | 拆出的新模块必须有**独立领域边界**，能一句话说清"它负责什么、原模块不负责什么" | 读新模块头注 + 对照 `AGENTS.md` 的领域描述 |
| 2 | **依赖严格单向** | 新模块 → 原模块单向；**反向 import 即成环** | `node scripts/audit-architecture.mjs --gate`（静态 + 动态环均须为 0） |
| 3 | **行为零改动** | 搬运过程中**守卫/判据逻辑逐条原样**，不得顺手"优化" | 逐条对照搬运前后（守卫条数、阈值常量、文案） |
| 4 | **消费方同步** | 所有 import 该符号的地方（含测试件）必须同步改 | 全局搜索该符号的所有引用点 |
| 5 | **行数确实下降** | 原模块行数必须下降，且新模块应低于冻结阈值（否则等于把问题搬了个家） | 跑 `check-module-growth` |
| 6 | **棘轮收紧** | 拆分后必须 `--rebase` **收紧**基线（只许收紧） | 跑 `check-module-growth`，确认基线已下调 |
| 7 | 未拆的模块有理由 | 仍超标而未拆的模块，必须逐条写明"为什么不拆" | 读交付记录 |

> 第 1 条是**否决项**：若新模块的职责无法用一句话说清，或拆完两个模块之间出现双向依赖，
> 就是**切错了接缝**——此时"行数好看了"不构成通过理由。**宁可让它大着，也不要制造碎片。**

### 6.2 连锁反应验收（拆模块必然触发，逐条确认）

拆出一个模块会牵动三类门禁，**它们报红通常是正确的**，验收时须逐条确认是"已同步"还是"真缺陷"：

| 门禁 | 预期报什么 | 正确处理 |
|---|---|---|
| 文件通道契约 | 原模块不再引用某介质 / 新模块引用但未登记 | 更新契约表的读侧 |
| 架构文档一致性 | 模块数变化 | 同步文档中的模块数声明 |
| 模块增长门禁 | 原模块低于基线 ⇒ 提示收紧 | `--rebase` 收紧 |

### 6.3 阶段 4 完成判据

- §6.1 七条全过
- §6.2 三条连锁反应均已处置（更新登记 / 同步文档 / 收紧基线）
- 通用验收项 §1 全部通过
