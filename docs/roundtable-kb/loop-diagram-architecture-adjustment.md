# 架构调整：循环图七框 ⟷ 106 模块对位

> **缘起**：用户给定「环境/任务/他人 → 感觉记忆 → 注意力门控 → 工作记忆 → 目标栈/中央执行 → 计划→执行→反馈→修正→巩固（循环）」及七条核心结论，要求**重点吸收做架构调整**。
> **性质**：决策态方案，不含施工。
> **证据**：全部为**本轮实测**（grep / 读码 / 命令输出），标位置与口径。
> **纪律**：引用 [原则] **档案事实须复验** —— 不凭印象判"哪层已实现"。

---

## 0. 一句话诊断

> **这张图是「阶段轴」（时间流：输入→门控→现场→调度→循环），现有架构是「域轴」（distill / deepsleep / panel / ring / supply…）。**
> 两轴**从未显式对齐** ⇒ 导致两个问题答不出：
> ① 「**这个阶段**由谁负责」——要跨 6 个域去追；
> ② 「**这个阶段的失败**在哪观测」——观测散在各域，最终表现为 §0.2 的"管道在写、判据没动"。

**⇒ 架构调整的方向不是重画域轴（骨架零环、深度 11 健康），而是补上这条缺失的「阶段轴」并让两轴相交。**

### 1.2 中央执行**七职责**逐条对位（✅ 实测，闭合 U3）

| # | 职责（图原文） | 实测命中 | 对位归属 | 判定 |
|---|---|---|---|---|
| ① | **选择当前目标** | `selectGoal\|currentGoal\|目标选择` = **0 处** | **L0 宿主**（`create_goal`/`todo_write`） | ⚪ **让渡**（与目标栈同源） |
| ② | 激活相关长时记忆 | `recallIndex\|recallRanked\|recallApprox` = **45 处** | `targets.ts` + `vec.ts` + `mcl.ts` | ✅ 有 |
| ③ | 分配工作记忆资源 | `budgetOf\|takeSlotLines\|levelCaps` = **43 处** | `supply-assembly.ts` + `budget-override.ts` + `panel-shared.ts` | ✅ 有 |
| ④ | 抑制无关干扰 | `crossform\|dedup\|coldFactor` = **91 处** | `crossform-dedup.ts` + `vec.ts`（冷因子 0.35）+ 六槽去重 | ✅ 有（命中最多） |
| ⑤ | 监控执行反馈 | `recall-yield\|zeroGain` = **48 处** | `recall-yield.ts` + `mcl.ts` | ⚠ **有代码，真机 `judged:true = 0`** ⇒ 出口断裂 |
| ⑥ | **切换上下文** | `contextSwitch\|carryOver\|handoff\|sessionSwitch` = **0 处** | **无** | ❌ **真缺**——但见下方判定 |
| ⑦ | 决定何时巩固/放弃 | `idleMs\|probeAfterMs\|consolidateTree` = **82 处** | `deepsleep-core.ts` + `distill-hooks.ts` + `deepsleep-tree.ts` | ✅ 有（水位三态、探测、树操作） |

**⇒ 统计：5 项有（②③④⑤⑦）· 1 项让渡（①）· 1 项真缺（⑥）**

**关于 ⑥「切换上下文」的判定**（**不盲目补**）：
- 图里"上下文切换"讲的是**人**在多任务间切换的代价（保存现场→加载新现场）；
- 本仓是**单会话 agent**，`mcl.ts` 已有**会话级隔离**（`state.delete(sid)`、跨会话不继承 `yield.verdict`）；
- 且外部基线的对照（`baseline` 席 R1）：**MemGPT/Letta 用 `interrupt` 显式建模上下文切换**，本仓无此概念 ⇒ **业界有先例，但本仓是单会话场景**；
- ⇒ **判定：属"真缺但优先级低"**——本仓的多会话并发由宿主（L0）承担，插件的"切换"需求不明确。**建议只登记，不本轮做**。

## 2. 架构调整方案（三项补件 + 两项让渡确认）

> **总原则**：**不动骨架**（零环/深度 11 健康），**补"阶段轴"的缺失实体**。

### 调整 1 · **注意力门控收口**（图中唯一"无主"的框 ⇒ 优先级最高）

| 项 | 内容 |
|---|---|
| **现状（实测）** | 四道门分处四文件，**互不知道彼此存在**：<br>`mcl.ts:642`（熟悉度 0.58）· `vec.ts`（冷因子 0.35）· `budget-override.ts`+`supply-assembly.ts`（容量）· `dynamic-select.ts`（选行） |
| **为何这是架构问题而非实现问题** | 图里「注意力门控」是一个**统一职责**（"决定什么信息能进入工作记忆"）；实现里它是**四份独立判据** ⇒ **没有任何一处能回答"这一步为什么放行/拦截"**。这正是"会掩盖其他问题"的形态：四道门各自静默，合起来无账 |
| **调整方式** | **新建 `attention-gate.ts`（纯函数区）**：把四道门的**判据声明**收口到一处（**只收口判据，不改各自实现**），产出一份 `gateTrace`（这一步过了哪几道门、被哪道拦住、为什么） |
| **落点** | **新建件**（不扩既有件）：`mcl` 导出 13/35、`vec` 9/35、`dynamic-select` 4/35 虽有余量，但**语义上这四道门分属四域** ⇒ 按"领域接缝"抽出更对 |
| **不撞棘轮** | 新件导出自由；**不需抬基线** |
| **验收判据** | `gateTrace` 在真机每一步可产出，且四道门的**放行/拦截计数**可按步统计 |
| **回归面** | 只加判据声明与留痕，**不改任何一道门的判定行为**（逐字节可回归） |
| **⚠ 必须先做的判定（✅ 已做，闭合 U1）** | 四道门**量纲根本不同**，**不可强行统一**（实测）：<br>· 门1 `mcl.ts:642` `sim >= familiarThreshold` —— **dense 余弦**（0–1 连续）<br>· 门2 `vec.ts:26` `coldFactor`（缺省 0.35）—— **降权乘数**<br>· 门3 `budget-override.ts:55` `capacityCharsOf()` —— **字符数**（整数）<br>· 门4 `dynamic-select.ts:32-39` —— **离散事件判定**（`new`/`session-changed`/`query-changed`/`compacted`）<br>⇒ 仓内**已有明文警告**同样的错（`criteria.generated.ts:165`：「本槽门控**不得复用** `surface.mcl.familiarThreshold`——那是 dense 相似度量纲，与任务键的**有/无离散命中**不是同一件事（复用即**量纲误用**）」）<br>⇒ **调整 1 只能走"并列登记 + 联合留痕"（Q1 的 B 选项），不得统一判据** |

### 调整 2 · **反馈循环闭合补件**（图里最核心的循环缺一环）

| 项 | 内容 |
|---|---|
| **现状（实测）** | `predicted` 782 条 / `outcome` 180 条 / `decisionId` 180/180 全配对，**但无比较机器** |
| **缺口精确表述** | 图里是「**比较**：预期 vs 实际」→ 一致则巩固、不一致则修正。本仓有"预期"字段、有"实际"字段、有"配对键"，**缺的正是那个比较动作** |
| **调整方式** | **新建 `calibration.ts`（纯函数）**：输入 `predicted` + `observed` → 输出命中/偏差/未判。与 `hit`（模型自报）**对照**，不替代 |
| **落点** | **新建件**（`decision-ring` 在 L2 且语义是"存储"；比较属"判据"⇒ 按领域接缝分开） |
| **验收判据** | 对现有 **180 条 outcome 回算**，与模型自报 `hit` 对照（当前 `hit` = 167/180 命中，若代码回算显著不同，说明模型自报不可靠 —— **这本身就是发现**） |
| **回归面** | 纯只读计算，不改库；`decision-ring` / `record-store` 均不动 |

### 调整 3 · **中央执行出口修复**（图中"调度与决策"的闭环）

| 项 | 内容 |
|---|---|
| **现状（实测）** | `judged:true` **0 行**（全三卷 50618 行）；`mcl-switch` 最后一条 **09-22T06:56:49Z**；`yield.verdict` 6/6 全 `unjudged` |
| **真死因** | 模型对每轮均判 `helped=null`（判不准）⇒ 出口锁死。**不是接线断**（写侧在跑） |
| **调整方式** | 见 `architecture-and-modules.md` §2.2 扩容点 2（判别力）——**提升 `buildYieldRequest` 材料** 或**换判据源** |
| **落点** | `recall-yield.ts`（导出 21/35 有余量）或新件 |
| **⚠ 回归面** | 改判据语义 ⇒ 须与 `landing-plan.md` §2 册一（先修 B2 观测能力）**同批**，否则改完不可观测 |

### 确认 1 · **目标栈让渡 L0**（不补）

| 项 | 内容 |
|---|---|
| **依据** | `docs/ARCHITECTURE.md:25` 原文：`L0 DSH 内核（不动）：agent-loop / session 事件溯源 / 压缩 / 沙箱 / goal / subagent` |
| **实测** | 全仓 `goalStack`/`taskStack`/`subgoal`/`子目标`/`目标栈` **0 命中**；本会话工具面确有 `create_goal`/`get_goal`/`update_goal`/`todo_write` |
| **判定** | **架构上正确**——插件不实现它，就是"让渡"而非"缺失" |

### 确认 2 · **感觉记忆让渡 L0**（但要澄清一处混淆）

| 项 | 内容 |
|---|---|
| **依据** | 输入缓冲 = 宿主 `session` 事件流（L0） |
| **⚠ 需澄清的混淆** | 插件侧的 `distill-chunks.ts` / `event-envelope.ts` **不是输入缓冲**——它们处理的是**已落盘的历史事件**，用于**离线蒸馏**。<br>⇒ 图里的"感觉记忆"是**当下这一步的原始输入**，而插件的这两个件是**事后批量消费** ⇒ **两者不是一回事，不可混称** |
| **判定** | 让渡 L0，但**文档与注释里"输入缓冲"的措辞须精确化**（避免下一个人把 `distill-chunks` 当缓冲） |

## 3. 调整后的架构视图（阶段轴 × 域轴）

> **这是本轮要交付的核心视图**——让两轴相交，从而"这个阶段由谁负责 / 失败在哪观测"可一眼答出。

      ↓

      ↓
注意力门控        →   ❌ 无主（四处散落）                          【调整 1】新建 attention-gate
