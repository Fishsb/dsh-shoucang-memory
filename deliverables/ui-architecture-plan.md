## 一、判因：架构层面的病

### 1.1 公共根（`arch` 归并，主持人采纳）

> **模块化只切了「文件」，未定义了「接缝」。**
> 契约（行形状 / 状态字段 / 词表注册 / 分层）**全落在文件之外**；每拆一次模块，就多一处**无人守的隐式约定**。

这不是"代码写得乱"，而是**架构缺一层**：拆了文件 ≠ 定义了边界。故表面症状虽多，收敛后只有四个投影。

### 1.2 四个投影（均带可引用行号）

| 成因 | 症状 | 关键依据 |
|---|---|---|
| **A｜行无模板** —— 行的形状由**调用方布尔开关**决定 | ① 标签位置两页相反（画像左／记忆库右）② `.sc-ctrl-meta` 112px vs **966px**、chip 左边界漂在 286/898/1066 ③ 行高 65/84/89/103 不齐 ④ 记忆库每行重复「22 条」 | `panes-memory.js:101` 的 `withTagCount`；`:132` 左列 vs `:137-143` 右列克隆；`ui-kit.js:36` `UI.item(...opts)` **四开关**；`.sc-ctrl-meta` 两条路 —— `panes-settings.js:25` 走 `extra` ⇒ 进 `.setting-item-info`（`styles.js:312` `flex:1;min-width:0` = **内容宽 112px**）vs `panes-toggles.js:45/95/129/541` 走 `children` ⇒ 挂 row 平级（`styles.js:316` `flex:none` = **拉伸 966px**）<br>**量化**：行容器 **5 套**（`.sc-crow`/`.sc-idx-row`/`.sc-kv-row`/`.sc-recent-row`/`.sc-row`）= **16 条 CSS / 15 处 JS**；chip **4 套**（`.sc-pill`/`.sc-badge`/`.sc-tag`/`.sc-chip`）= **17 条 CSS / 7 处 JS** |
| **B｜状态双份** —— `appState` 声明面 ≠ 注入面，**字段名零校验** | 跨模块句柄拼错 = 静默 `undefined` | `app-state.js` 声明 **20** / `body.js:1003-1020` 注入 **24** / **7 个字段无声明行**（`deferFold` `filterViewRows` `flushFolds` `makeToggle` `metaBadges` `show` `switchKeys`）/ 反向穿透：`pollTimer` 声明在容器、唯一写点在 `panes-settings.js:199,202` / **无门禁**：`audit-pane-deps.mjs:36-41` 把 `appState` 当服务整体放行、不校验字段名。全仓引用 **291 处** |
| **C｜注册无契约** —— 「文件存在 ≠ 已注册」（**功能缺陷，非风格**） | 英文态 7/9 视图仍显示中文 | `body.js:33-34` 只 import NAV+MEM；`cfg`(283)/`pane-run`(231)/`pane-arch`(186) **import 次数 = 0**；产物命中率实测 **1% / 3% / 3%**；`check-i18n-keys.mjs:35` `DICT_FILES` 硬编码、断言 H（`:270-288`）只查「目录⟷清单」。**影响**：未注册 700 键 vs 已注册 223 键；**英文态仍中文的界面串 752 条（唯一键）**，逐文件 toggles 182 · overview 154 · arch 128 · observe 108 · settings 76 · suite 61 · config 22 |
| **D｜分层未定义** —— 前端从未被分层门禁扫过，环已存在 | 共享裁决者无处安放 ⇒ 退化成调用方布尔开关（即 A） | `audit-architecture.mjs:27` 默认 `REL='src'`；`check-runner.mjs:360` 登记未带 `--dir`；手动 `--dir src-client --gate` 报 **1 处双文件双向环** `panes-memory.js:13 ↔ panes-memory-detail.js:16`；全部模块被打 `??`（无层级） |

### 1.3 三方关系澄清（避免误读为「四个独立毛病」）

- `minimal` 的「同一语义重复渲染」= 成因 **A** 的显示层表述
- `maint` 的「`appState` 服务定位器为最大病灶」= 成因 **B**
- ⇒ 它们是**同一归并下的两个投影**，不是平行成因。归并件 = `arch`。

> ⚠ 数字更正：`maint` 报「`appState` **27 字段**」**不可用**；主持人与 `arch` 双测一致为 **声明 20 / 注入 24 / 无声明 7 / 引用 291 处**。

## 二、目标架构：四条接缝

优化方案的每一阶段，都对应**定义一条接缝**。这是本方案与"按症状打补丁"的分界。

| # | 接缝 | 定义什么 | 收敛手段 | 判据 |
|---|---|---|---|---|
| **接缝①** | **行形状契约** | 「一行是什么」——左主文本 + 右槽 `.sc-right` 的**唯一形状** | 形状收进 `ui-kit.js` **具名变体**（如 `UI.indexRow({tag,subject,pointer,right})` / 变体 `inline-chip`），**删 `withTagCount` 与 `UI.item` 的四开关** | 行容器 5→1；chip 4→1；调用方不再传布尔 |
| **接缝②** | **状态契约** | `appState` 的**字段集**＝声明面＝注入面 | 补齐 7 行声明 + 收回 `pollTimer` 写点 + **加键集双向门禁**（声明 ∪ 注入 ∪ 消费 三方对账） | 门禁红＝字段名拼错或契约外字段 |
| **接缝③** | **注册契约** | 模块/词表的**注册是自动的**，不靠人记得改清单 | 词表按**目录自动发现**注册；消灭「文件存在 ≠ 已注册」 | 新增词表文件无须改任何清单即生效；门禁在**产物层**验「已注册」 |
| **接缝④** | **分层契约** | 前端也有层级与依赖方向，且**被机检** | **先破环**（`panes-memory ↔ panes-memory-detail`）→ **再加门**（`--dir src-client`） | `audit-architecture --dir src-client --gate` 零环 |

**架构不变量（本方案的验收底线）**
1. 不推倒重写（见 §六 不做什么）
2. 不破坏现存机检资产：运行器摘要行 **`PASS（135 pass · 0 xfail · 0 skip）`** + 三条 i18n 红线（`check-i18n-redlines` R1–R4）
3. 不改真源数据（`_memory/` / 库文件）
4. 每阶段**可独立验收 + 有回滚**（回滚点 `66a1535` = 现 HEAD = profile pin）

## 三、优化方案：分期

> **编号与本文件的接缝一一对应**（不沿用 `rollout` 的 P0–P5 —— 它按"清场→归→chip→逻辑→视觉→backlog"切，
>   本方案按"**缺陷 → 清场 → 接缝①②③④ → backlog**"切，边界来源是架构而非症状）。

| 项 | 内容 |
|---|---|
| 成因 | **C** —— 这是**功能未达标**，不是风格问题 |

## 六、不做什么（防滑坡 / 防扩面）

| 不做 | 依据 |
|---|---|
| **不推倒重写** | `steelman` 构造完整反方案后判「**未找到更优替代**」：复杂度/交付时间/风险/生态版本耦合**四维更差**，且**结构上无法满足"每阶段可独立验收"**（宿主每包只加载一个 client bundle，双轨不成立；切一半 ⇒ UI 冻结 + 门禁/几何门全红 ⇒ 按规则 7 判未完成）。**5:0 一致** |
| **不引入 React/TSX** | 生态小插件同为纯 JS（`wallpaper-engine .js:52` / `prompt-enhancer .cjs:14` / `free-search`·`edit-diff` 各 2 件）⇒ 纯 JS 在生态内不异常；且 TSX 化会把 135 项机检资产置于重写风险（`lib-client-src.mjs:31,41` 的 `.js` 过滤会让 3 件门**静默失明**、`check-module-growth.mjs:54-56` 冻结表整体失效、`ui-geo-regress`（906 行）需换真 react 且断言 31 个 `.sc-*` 选择器） |
| **不合并视图 / 不减 Tab** | `user` 实测结论：学习成本的问题在**每页各一套行布局**，**不在视图数量**（9 个一级视图本身不构成负担）。无用户面证据支撑 |

## 附：对 `minimal` M1「行容器 5 套 → 1 套」的**反证与撤回**（2026-09-17 · 施工期实测）

**结论：M1 的前提不成立，本项撤回，不做合并。**

`minimal` 的判据是「`.sc-crow`/`.sc-idx-row`/`.sc-kv-row`/`.sc-recent-row`/`.sc-row` **各写各的**，
统一为『左主文本 + 右槽』」。施工期逐类核对 CSS 后，**五个类不是同一语义的五套实现，而是五种语义**：

| 类 | 实际语义（实测 `styles.js`） |
|---|---|
| `.sc-row` | **表单行**：`flex:none`、无内距、无下边框 |
| `.sc-crow` | **卡内行**：有内距（`10px 14px`）+ 下边框 + hover |
| `.sc-kv-row` | **`display:contents`** —— 不是行容器，只是给一组子元素打标的占位类 |
| `.sc-idx-row` | **可点击索引行**：`cursor:pointer` + hover + 圆角 + 4px 内距 |
| `.sc-recent-row` | 小字号单行文本 |

**决定性证据**：`src-client/styles.js:596` 的**原有注释**已经写明了为什么必须分开 ——

> 卡内行（原型 `.card > .bd .row`）：**不能复用 `.sc-row`** —— 后者是表单行语义
> （`flex:none`、无内距无下边框），**混用会把表单布局带坏**。故单列 `.sc-crow`。

⇒ **强行 5→1 会破坏「表单行 / 卡内行」这一刻意分离**，把已知的布局陷阱重新引入。

**保留的真实问题（改名可解，但收益低于风险，列为 backlog）**：类名**不表达语义** ——
`.sc-row` 是表单行、`.sc-crow` 是卡内行，名字完全没体现，新读者极易混用。
若要收敛，正确做法是**按语义改名**（如 `.sc-form-row` / `.sc-card-row`），而非合并；
但那会改动大量 CSS 选择器，收益（防误用）低于成本，**不在本方案阶段 2 内做**。

**方法论意义**：这是「**实证否判**」的一次实际应用 —— 专家的结论须经施工期实测复核；
本项若盲从，会以"统一"之名破坏一个**已被注释记录过教训**的刻意分离。
