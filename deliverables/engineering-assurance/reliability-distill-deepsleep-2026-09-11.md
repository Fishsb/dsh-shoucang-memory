## 1. 四问逐条回答

### Q1 定时调用前实例没启用端口 → **伪命题（🟢 无风险）**

- **证据**：`src/**` 全文 grep **无任何 3080 引用**（仅 Ollama `11434` 可选 embedding，且 `try/catch` 降级）。LLM 调用是进程内 `ctx.subagents.start('spawn')`（`distill.ts:1245` / `:2507`），脚本调用是 `spawn(node, script)`，写入是 `node:fs`——**全程无 HTTP**。面板才依赖 `ctx.webServer`，且缺失时 `warn + return`（`panel.ts:89-92`），不影响调度。
- **性质**：不是"跳过一轮"，是**静默黑洞**——停机 3 小时 = 3 小时零巡检、零蒸馏，且**没有任何组件记录"我本该跑但没跑"**（全仓 grep `heartbeat|deadman|missed` 零命中）。
- **真实版本**：日志里有 **端口被占用**（非未启用）的实证案例，见 §4-(a)。

### Q2 执行中被打断 → **🟢 有防护，实证有效**

- **定时器生命周期干净**：深睡巡检（`:3075`）、积压扫尾（`:3105`）、自检（`:3085`）、idle（`:2872`）**全部挂在 `ctx.effect`**，cordis 4.0.0-rc.9 的 `ctx.on` 内部也走 `fiber.effect`（`node_modules/cordis/lib/index.js:337-344`）。热重载**不留幽灵 tick**——这推翻了我派单时的假设。
- **实证 22 次打断全部安全**（`09-09T16:24` ~ `09-10T01:01`）：
  ```

  distill: 5f024550 段3 旧 ctx 已失效（inactive context），跳过本轮（水位保留 65852，待扫尾）
  ```

  防护动作统一为「**跳过本轮 + 水位保留/回退**」⇒ 下轮重扫，不丢。

## 2. 发现的缺口（按严重度）

### 🔴 D1 — `dispatch-failed` 与重复写入（**经二次复核后定性已修正，见下方 ⚠️**）

> ⚠️ **本条定性经过一次翻案，务必读完**：初版（Rex）判定为「104 条静默丢失、不可恢复」，**该定性错误**。Archi 提出异议后，我（Zhen）用「代码分支 + 日志计数」双向复核，**裁定 Archi 正确**。原始统计保留如下，但**结论已改写**。

- **原始统计**（`distill-audit.jsonl`，220 个有结局的蒸馏轮次，Rex 产出，数据本身无误）：

  | fclass | 轮次 | completed | added | failed |
  |---|---|---|---|---|
  | **dispatch-failed** | **52** | **52/52** | 94 | **104** |
  | gate-reject | 49 | 49 | 30 | 0 |
  | ok | 44 | 44 | 120 | 0 |
  | discard | 61 | 61 | 0 | 0 |
  | json-parse | 4 | 2 | 0 | 0 |

- **❌ 错误定性（Rex）**：「`stop=completed` ⇒ 判为 done ⇒ 104 条静默丢失、水位照推、不可恢复」。
  该推断的依据是**测试件**（`scripts/test-*.mjs`）里的状态机表述 `attempted>0 且 stop=completed ⇒ done`，**那不是运行时逻辑**。
- **✅ 正确定性（Archi 提出，Zhen 用代码 + 日志双向复核裁定）**：运行时是 `distill.ts:1308` / `:1314` 两条互斥分支：
  ```js
  if (stop === 'completed' && out && disp.failed === 0) { …推水位… }        // :1308
  else if (stop === 'completed' && out && disp.failed > 0) {                // :1314
    const tries = (dispatchFailStreak.get(streakKey) || 0) + 1
    if (tries >= MAX_DISPATCH_RETRY) { …强制推进 + 落 dispatch-failed-forced… }
    else { dispatchFailStreak.set(streakKey, tries); log('…水位保留，下轮从本段续传') }
  }
  ```
  **`disp.failed > 0` 时水位保留、不推进**——该分支注释明写「A1（**2026-09-11 审查修复**）」，即**今天刚加的防护**。
- **日志实证（决定性）**：
  ```
  第 1/3 次重试: 4    第 2/3 次: 0    第 3/3 次: 0
  强制推进水位: 0     dispatch-failed-forced: 0
  ```
  `第 2/3 次 = 0` ⇒ **每次落盘失败后，下一轮重蒸就成功了**，`dispatchFailStreak` 从未累积到 2，**强制推进路径从未触发**。
- **真实后果**：数据**没有丢**（水位保留 ⇒ 下轮重蒸），代价是**重复写入**——实测 `索引行重复 8 条`。原因是水位保留要重蒸整段，而 `memory-append.mjs` 的 appends 通道**无幂等键**。
- **修法**：给 appends 加内容指纹幂等键（复用已有 `intentTokens`），或宿主 `writeDispatch` 落 stub 指纹后重蒸前比对。**不需要改 `stop` 语义**。
- **同类（这些才是真·不可自动恢复）**：「新索引超容量不写」62 次、「落点失败」24 次、「ENOENT 直写失败」18 次 —— 均需人工介入（合并下沉 / 建顶层锚点 / 建目录）。

### 🔴 D2 — 深睡水位重启即丢料（**Archi 与 Cody 独立得出同一结论，Zhen 已复核**）

- **机制**：`lastDeepSleepAt` 纯内存，重启靠审计回放（`:1402-1419`）。回放过滤：
  ```js
  o.kind==='deep-sleep' && !o.error && o.stop!=='error'
    && !['no-parent','no-traces'].includes(String(o.result))
  ```
  注释写「只回放**确实消化过痕迹**的深睡」——**意图正确**，但排除名单只覆盖「无事可做」，**没覆盖「做了但失败」**。
- **实测**：38 条深睡行中仅 20 条带 `result`，值全是 `no-traces`/`no-parent`。今日五轮：
  ```
  08:32  attempted=3  added=0  gate=all-rejected  result=None  ← 失败
  08:48  attempted=1  added=0  gate=all-rejected  result=None  ← 失败
  08:50  attempted=1  added=1  gate=pass          result=None  ← 成功
  ```
  `String(undefined)` = `'undefined'`，**不在排除名单内** ⇒ 失败轮被当有效水位回放。
- **进程内判据与回放判据不一致**：进程内用 `deepSleepLanded`（`distill.ts:354-358`，看 `added`/`attempted`/`gate`），回放**不看这些**（`:1413-1416`）。
- **后果**：同进程靠内存回滚能重试（08:32→08:48→08:50 三轮实证），**但中间只要重启一次**，那批材料永久出窗。
- **修法**（极小）：回放复用 `deepSleepLanded`；或审计行补 `result: landed?'done':'failed'`。**~2 处小改**。

### 🔴 D3 — 主写入通道非原子（Cody 发现，Zhen 复核后裁定 Archi 说法不完整）

- **事实**：宿主侧原子纪律整齐（`distill.ts` 的 `atomicWrite` 家族 `:808/:1613/:1762`、`treeops.ts:146` 全 tmp+rename）。**但蒸馏 90% 的写入走 `memAppend` → 外部脚本 `memory-append.mjs`**，其末行是：
  ```js
  await writeFile(filePath, content, 'utf8');   // :148 —— 直接覆盖，无 tmp、无 rename
  ```
  仓内与库根是同一份（sha `33df7ab4f823` 一致），**不是部署漂移，是设计如此**。
- **兜底**：写前 `copyFile` 到按分钟戳的备份目录（`:37`，`catch {}` 尽力行为），实测已堆积 **98 个备份目录、无清理**。
- **放大因素**：`memAppend` 走 `runNode` 起**独立 OS 进程**，父进程被杀**不会**连带杀死子进程。
- **修法**：脚本末行改 `writeFile(tmp)` + `rename(tmp, filePath)`；或宿主侧读全文→拼接→走自己的 `atomicWrite`。**1 个脚本 1 行**。

### 🟠 D4 — 并发防护有破口（Cody 发现）

- **`tryClaim` 是 TOCTOU**（`:1070-1079`）：`readFileSync` 判 TTL → `writeFileSync` 写 claim 两步非原子，同 tick 内两个 fiber 可各自拿到锁 → **双蒸馏**。修法：`writeFileSync(f, body, { flag: 'wx' })`（单行）。
- **深睡完全没有跨实例锁**：只有内存 `deepSleepRunning`，无 claim 文件。多代并存时两个实例用同一 `since` 各跑一次归纳；且 `applyPrinciples` 的 tmp 名固定为 `AGENT.md.tmp`（`:1613`），两实例互相覆盖 tmp，可能把对方被拒收的内容 `renameSync` 进正式文件。
- **写侧不幂等**：`memory-append.mjs:129` `lines.splice(insertPos, 0, ...)` **无去重**（`grep dedup` 零命中）。索引行有唯一性硬门（`distill.ts:877-921`，精确/词法 0.66/向量 0.80 三重），**notes 正文 append 没有**。

### 🟠 D5 — 失败重试无上限 / 无退避 / 无死信

- 段失败靠 10min 巡检**无上限重试**；唯一上限 `MAX_DISPATCH_RETRY=3`（`:1059`）只覆盖"落盘失败"子类，且 `dispatchFailStreak` 是**内存态、重启清零**（`:1060`）。
- 无指数退避、无抖动、无 dead-letter。真库某段恒定失败 ⇒ **每 10min × 每个 root 一次 spawn，永不停止**。
- 注：`distill.ts:733` 的 `1500ms × 3` 是 `resolveWorkspace` 的**转录定位**重试，**不是 LLM 重试**（我与 Archi 都误读过）。

### 🟠 D6 — 无可观测性：连调度器死活都判断不了（Rex 实测）

- 无心跳、无死人开关。当前状态：**面板应答 200、`running=3`、`reload fail=0` ⇒ 存活**，但日志已静默 11 分钟，**无任何证据证明它还在 tick**。

- **结论：这不是"调度器有问题"，而是"没有任何数据能回答这个问题"**——可观测性缺口本身。

## 3. 三个"反直觉"结论

1. **219 次启动不是宿主重启，是热重载**。Rex 把 `reload-debug.log` 与「distill 启动」做时间配对：窗口内 reload 130 次，**reload ±30s 内有 distill 启动 = 128/130（98%）**。日志跨度 93.3h，若真是 10min tick 应打出 ~560 条，实际 214 ⇒ **「启动」是装配事件而非 tick**。
2. **审计字段与运行时逻辑不是一回事**：`stop=completed` 只是**子代理的返回码**，审计再单独记 `fclass='dispatch-failed'`。两者从不交叉判定——**判"是否消化"看的是 `stop` + `disp.failed` 的组合分支（`:1308`/`:1314`），不是 `stop` 单值**。Rex 正是误把测试件里的状态机当成了运行时逻辑。
3. **同类缺口真正的代价是"重"不是"丢"**：水位保留 ⇒ 下轮重蒸 ⇒ 数据回来了，但 appends 无幂等键 ⇒ 重复。实测 `索引行重复 8 条`。
3. **"看起来有防护、实际在主通道上无效"**——这是本次审查反复出现的模式：宿主原子写入很整齐，但主通道是外部脚本的非原子覆盖；深睡水位有回放恢复，但回放判据漏掉了最该排除的失败轮。**与今日下午修的 B0（守卫失配）是同一类病**。
