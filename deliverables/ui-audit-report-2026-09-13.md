### 1.4 数据/UI 健壮性层（B−）

**唯一发现的真问题**：`renderIndexRows`（body.js:2716）对 lines 数组的元素做属性解构：

```js
arr.forEach(function (ln) {
  var row = el('div', 'sc-idx-row');
  row.appendChild(idxPill(ln.tag));          // undefined
  row.appendChild(el('span', 'sc-idx-subject', ln.subject || ''));
  if (ln.pointer) row.appendChild(...);
  ...
});
```

当 `lines` 是 `['[x]', '[x]', ...]`（纯字符串，**当前 mock 数据格式**）时：

- `ln.tag`/`ln.subject`/`ln.pointer` 全为 undefined
- 仍然创建 row，行内容为**空 pill + 空文本 + 无指针**
- 但 row 仍渲染（**占位 25px 高**）

**截图佐证**：
- USER.md 容量卡写"24 条画像"，实际渲染 **17 行**（少了 7 行？或者 mock lines 是 new Array(24) 但 renderIndexRows 漏掉部分？）
- AGENT.md 容量卡写"19 条画像"，**整张卡找不到**——可能卡本身存在但被截到屏幕外，也可能是 renderPersona 对 AGENT 抛错

**根因**：mock 数据结构与 UI 期望不对齐。**真机数据是结构化的 `{tag, subject, pointer}`，所以线上没问题；但 mock 测试时暴露了这个潜在脆弱性**——如果未来某条数据真的退化（缺字段），UI 会出现「空行」或「整库消失」。

**修复路径**：`renderIndexRows` 在 `!Derive.has(ln)` 时跳过该行并 `console.warn` 一次（项目已有 `Log.warn`）；或在 `pairs.forEach` 里检测 `Derive.has(f.lines)` 失败时**显式标注**。

## 3. 审查方法论（值得记下来的两点教训）

### 3.1 看图要交叉验证

我第一次看图时报告了 4 个"问题"，**其中 2 个是误判**：
- "画像 AGENT 库无指针列表" → 代码逻辑正确（pair.forEach 都建卡），实际是 viewport 截短
- "设置页缺启动时视图" → 代码存在（body.js:3559），实际是 viewport 截短

教训：**视觉发现必须回查代码根因**。只看代码拿不到视觉问题，只看图会制造伪问题——这两类错误分别损害"完整性"与"准确性"，都很危险。

### 3.2 估算 vs 实测系统性偏差

首版落实方案里我用 grep 行号差估算跨度，**普遍偏大**：

| 函数 | 估算 | AST 实测 | 偏差 |
|---|---|---|---|
| `renderSuite` | 165 | 101 | +63% |
| `buildModal` | 125 | 93 | +34% |
| `renderMemoryExpanded` | 331 | 321 | +3% |
| `renderViewToggles` | 616 | 615 | 几乎一致 |

偏差来自函数间注释与空行被计入。**凡是要写进门禁的数字都先实测**，不能相信 grep。
